# P5 定时订阅与增量推送

## 目标

P5 实现含发送时间或频率的自然语言问题订阅化。系统能够把订阅写入数据库，由 APScheduler 按计划触发，也支持在 Web UI 中手动触发订阅；每次订阅运行都会生成可下载、可追踪、可验证的 Word 文件。

本阶段的关键验收点是增量不重复：同一个订阅已经推送过的招标信息会写入 `sent_history`，后续再次运行时只输出新增内容。没有新增内容时仍生成一份 Word，用于证明本次定时任务已经执行且没有新公告。

## 新增模块

- `tendertrace/scheduling/subscriptions.py`：订阅创建、查询、运行入口。
- `tendertrace/scheduling/scheduler.py`：APScheduler 后台调度器和 cron/date trigger 映射。
- `tendertrace/scheduling/ledger.py`：`sent_history` 增量账本。
- `tendertrace/runner.py`：新增 `subscription_id` 与 `incremental` 参数，复用同一条 `intent -> collect -> report` 图运行链路。
- `tendertrace/app/api.py`：新增订阅 API，并在 FastAPI lifespan 中启动和关闭调度器。
- `web/dist/*`：新增订阅创建、订阅列表、手动触发、outbox 追踪入口。

## 启动方式

如果 8000 未占用：

```powershell
python -m tendertrace serve
```

如果 8000 已占用：

```powershell
$env:TENDERTRACE_PORT='8001'
python -m tendertrace serve
```

访问：

```text
http://127.0.0.1:8001/
```

如需临时关闭后台调度器，仅保留 API 手动触发：

```powershell
$env:TENDERTRACE_SCHEDULER_ENABLED='false'
python -m tendertrace serve
```

## UI 工作流

1. 输入带发送频率的自然语言问题，例如：`最近36个月上海设备招标信息，每天9:00发送给我`。
2. 设置最大翻页数和最大结果数。
3. 点击 `创建订阅`。
4. 在订阅表中确认计划字段，例如 `0 9 * * *`。
5. 点击该订阅的 `手动触发`。
6. 等待运行摘要变为完成，查看 notice 数、trace 事件数和 checkpoint。
7. 在 outbox 中下载本次 Word 文件。
8. 再次点击同一订阅的 `手动触发`，如果源站返回同一批公告，notice 数应为 0，证明 `sent_history` 生效。

## API 契约

创建订阅：

```http
POST /api/subscriptions
Content-Type: application/json

{
  "query": "最近36个月上海设备招标信息，每天9:00发送给我",
  "max_pages": 1,
  "max_results": 2
}
```

返回核心字段：

```json
{
  "id": "71247c7e-947e-4862-bdb4-9020276e32fb",
  "original_query": "最近36个月上海设备招标信息，每天9:00发送给我",
  "schedule_kind": "recurring",
  "cron": "0 9 * * *",
  "timezone": "Asia/Shanghai",
  "status": "active"
}
```

列出订阅：

```http
GET /api/subscriptions
```

手动触发订阅：

```http
POST /api/subscriptions/{subscription_id}/run
```

典型第一次运行返回：

```json
{
  "status": "finished",
  "notice_count": 2,
  "trace_events": 10,
  "outbox_path": "D:\\超聚变\\outbox\\最近36个月上海设备招标信息，每天9_00发送给我_202607061805.docx"
}
```

同一订阅第二次运行若无新增公告：

```json
{
  "status": "finished",
  "notice_count": 0,
  "trace_events": 10
}
```

## 增量去重验证

数据库表关系：

- `subscriptions` 保存订阅的原始问题、BidQL、cron、状态和最近运行时间。
- `runs` 保存每次运行，订阅运行的 `mode` 为 `incremental`，并写入 `subscription_id`。
- `outbox_messages` 保存 Word 文件和对应的 `run_id`、`subscription_id`。
- `sent_history` 保存每个订阅已经推送过的 `cluster_key`。

可用 SQL 检查：

```powershell
python - <<'PY'
from tendertrace.config import Settings
from tendertrace.db import connection

settings = Settings.load()
with connection(settings) as conn:
    print("subscriptions", conn.execute("select count(*) from subscriptions").fetchone()[0])
    print("sent_history", conn.execute("select count(*) from sent_history").fetchone()[0])
    print("latest runs")
    for row in conn.execute("select id, subscription_id, mode, stats_json from runs order by started_at desc limit 3"):
        print(dict(row))
PY
```

预期表现：

- 第一次订阅运行：`stats_json.new > 0`，`sent_history` 增加对应 cluster。
- 第二次订阅运行：相同 cluster 不再进入报告正文，`stats_json.skipped_sent > 0`。
- outbox 仍新增一份 Word，用于证明本次定时/手动任务已执行。

## 已知边界

- 当前 P5 的发送渠道仍是 Web 下载 + 本地 outbox；真实邮件、企业微信、Slack 等推送渠道属于后续阶段。
- `sent_history` 以订阅为维度去重，不同订阅之间不会互相抑制。
- 订阅触发当前仍同步执行采集和报告生成。后续如果接入大量源站，应加入任务队列和后台 worker。
- `once_at` 订阅当前按服务启动时当天目标时间计算；如果目标时间已过，会立即执行。
