# P7 清洗去重与聚类账本

## 目标

P7 解决多源采集后的重复与噪声问题。系统现在会在采集后统一执行正文清洗、URL 规范化、项目编号提取、SimHash 计算、跨源聚类和 SQLite 账本落库。

本阶段不改变各来源适配器的职责。`ccgp`、`ggzy`、`qianlima` 仍只负责抓取候选公告；`pipeline.dedup` 负责把候选公告变成干净、可聚类、可增量去重的公告对象。

## 新增模块

- `tendertrace/pipeline/dedup.py`：清洗、规范化、SimHash、标题相似度、项目编号提取、聚类合并。
- `tendertrace/runner.py`：在 collect 节点中接入 `clean_and_cluster_notices()`，并写入 `notices` 与 `clusters` 表。
- `tendertrace/report/docx_writer.py`：报告中展示合并后的关联来源。
- `tests/test_pipeline_dedup.py`：纯函数测试。
- `tests/test_runner.py`：验证 runner 写 run stats 与 cluster 账本。

## 清洗与去重策略

清洗：

- 移除常见页面噪声，如 `打印本页`、`关闭窗口`、`友情提示`、`免责声明`。
- 合并多余空白。
- 标题去掉公告类型后缀，如 `公开招标公告`、`采购公告`、`中标公告`。

规范化：

- URL 统一小写 scheme/host。
- 去掉 fragment。
- 去掉 `utm_*`、`spm` 等追踪参数。

聚类：

- 优先按项目编号合并。
- 其次按 canonical URL 合并。
- 再按归一化标题 + 发布日期合并。
- 最后用标题 bigram 相似度和 SimHash 汉明距离判断近似重复。

入库：

- `notices` 表保存清洗后的主公告。
- `clusters` 表保存聚类键、项目编号、标题归一化、发布时间和关联来源。

## 已知边界

- 当前聚类是保守策略，宁愿少合并，也不把不同项目误合并。
- 跨源同项目但标题差异极大、项目编号缺失时，可能暂时不会合并。
- `clusters` 表保存当前主公告和关联来源，但还没有独立的人工审核界面。
- 下一阶段应增强证据链，把字段级来源 span、原文快照和事实一致性校验补齐。
