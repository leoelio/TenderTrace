# P9 附件下载与正文抽取

## 阶段目标

P9 在 P8 证据链基础上补齐附件处理能力：

- 下载公告中的附件链接并缓存到 `snapshots/attachments/`。
- 为附件计算 SHA256，避免同一文件无法追踪版本。
- 从 PDF、DOCX、XLSX 中抽取可用正文片段。
- 将附件下载、解析、失败、跳过状态写入 `attachment_snapshots` 表。
- 将附件正文片段合入证据链，辅助核心内容事实校验。
- 在 Word 报告中展示附件解析汇总和附件正文摘录。
- 在 Web 运行状态中展示附件正文抽取数量。

## 成功标准

1. `pipeline.attachment_extract` 事件出现在运行 trace 中。
2. `runs.stats_json` 包含 `attachments_seen`、`attachments_attempted`、`attachments_downloaded`、`attachments_extracted`、`attachments_failed`、`attachments_skipped`。
3. `attachment_snapshots` 表有文件级账本记录。
4. Word 报告包含 `附件解析` 和可用的 `附件正文摘录`。
5. Web UI 运行状态显示 `附件正文` 指标。
6. 全量测试和 Ruff 均通过。

## 核心文件

- `tendertrace/pipeline/attachments.py`：附件下载、缓存、PDF/DOCX/XLSX 正文抽取。
- `tendertrace/pipeline/evidence.py`：把附件正文片段合入证据链。
- `tendertrace/runner.py`：在 evidence 节点内先执行附件处理，再执行事实校验。
- `tendertrace/db.py`：新增 `attachment_snapshots` 表。
- `tendertrace/report/docx_writer.py`：Word 展示附件解析状态和附件正文摘录。
- `web/dist/index.html`、`web/dist/app.js`、`web/dist/styles.css`：运行状态面板增加附件正文指标。

## 执行顺序

P9 后的关键流水线：

```text
collect
  -> clean_and_cluster_notices
  -> enrich_attachment_snapshots
  -> attach_evidence
  -> persist notices / clusters / evidence / attachment_snapshots
  -> sent_history incremental
  -> report
```

附件处理放在 `attach_evidence` 前面，因为附件正文可以成为事实校验的证据来源。

## 附件安全阈值

`.env.example` 新增：

```env
TENDERTRACE_ATTACHMENT_MAX_PER_NOTICE=3
TENDERTRACE_ATTACHMENT_MAX_BYTES=8388608
```

含义：

- 单条公告最多下载 3 个附件。
- 单个附件最大 8 MB。

超过阈值的附件不会让任务失败，会写入 `skipped` 状态。

## 支持格式

当前正文抽取支持：

- PDF：`pypdf`
- DOCX：`python-docx`
- XLSX：`openpyxl`

其他格式如 DOC、XLS、ZIP、RAR 会保留链接并记录 `skipped`，不下载正文文件，也不做正文抽取。

## 验收观察点

运行任务后检查：

- `outputs/` 中新 Word 是否存在。
- `outbox/` 是否有同名可下载文件。
- Word 中是否出现 `附件解析`。
- `attachment_snapshots` 表中是否出现附件记录。
- Trace 中是否出现 `pipeline.attachment_extract`。
- Web 运行状态中 `附件正文` 是否显示抽取成功数量。

## 当前限制

- PDF 使用文本层抽取；扫描版 PDF 需要后续 OCR 阶段。
- DOC、XLS、ZIP、RAR 当前不下载正文文件，不做正文抽取。
- 附件下载失败不会中断整次报告生成，而是记录 `failed` 状态。
