## 一、目标与验收口径

本方向解决“决定投标之后，团队具体怎么完成”的问题。系统不再只给出一份长文摘要，而是把招标文件中的要求转成一套可执行对象：要求、交付物、责任人、证据、内部节点、飞书任务、报价项和完成状态。

验收成功标准如下：

1. 覆盖资格、截止、评分、废标、附件五类高价值要求，并扩展技术、商务两类要求。
2. 每条要求均保留原文、来源链接、原文定位、强制属性、权重、置信度、状态、责任人、截止时间和来源修订标识。
3. 人工可以确认、拆分、合并、修订要求，所有变动都有历史记录。
4. 只有人工确认的要求才能生成正式交付物和任务。
5. 自动生成交付物清单、RACI 责任矩阵、截止倒排计划、任务依赖、缺口泳道、废标红线和报价计划。
6. 飞书任务和日历同步必须幂等；飞书任务完成后可以回写本地执行状态。
7. 任务完成度必须进入数字孪生的投标准备度，并给出可解释计算依据。
8. 可导出要求目录、交付物、RACI、倒排计划、缺口和报价，且全程沿用同一要求 ID。

## 二、市场产品调研与界面取舍

本次没有照搬单一产品，而是组合三类成熟做法：

- [Loopio Projects](https://support.loopio.com/hc/en-us/articles/360023671294-Getting-Started-Projects) 的文档导入、协作回答和原格式导出思路，用于建立“原文要求—响应内容—输出文件”的连续链路。
- [Asana Work Breakdown Structure](https://asana.com/templates/work-breakdown-structure) 和 [Work Plan](https://asana.com/templates/work-plan) 的工作分解、责任人、截止时间、依赖、里程碑和阻塞关系，用于构建倒排作战计划。
- [monday.com RACI Matrix](https://monday.com/templates/raci-matrix) 的 R/A/C/I 责任分工，用于明确执行、批准、会签和知会角色。

最终界面采用一个紧凑的深色作战区：顶部显示关键指标，中部并排展示要求树、缺口泳道、交付物、RACI、倒排时间轴和报价计划，底部保留人工修订历史。评委可以在同一区域看清“为什么做、谁来做、何时完成、缺什么、完成后怎样改变准备度”。

## 三、功能交付清单

### 3.1 要求结构化与来源追溯

已实现七类要求：资格条件、截止时间、评分项、废标条款、附件清单、技术参数、商务条款。

每条要求保存以下字段：

| 字段 | 作用 |
|---|---|
| 要求 ID / 编号 | 串联交付物、RACI、任务、报价和导出记录 |
| 原文摘录 | 防止模型概括替代正式依据 |
| 来源链接 / 原文定位 | 支持点击回到公开页面或文件位置 |
| 强制项 / 评分权重 | 识别废标风险和得分价值 |
| 置信度 / 提取方式 | 区分规则、OCR、模型和人工录入 |
| 来源修订 ID | 关联公告版本，便于变化复核 |
| 状态 / 责任人 / 截止时间 | 进入执行闭环 |

金额、日期、“须”“不得”“无效”“满分”“签字”“盖章”等强信号由规则优先识别。没有可靠文本时，接口返回 `ocr_or_manual_required`，不会伪造结构化要求。

### 3.2 人工确认、拆分、合并与历史

已实现：

- 单条要求人工确认；
- 复杂要求拆成两条或多条原子要求；
- 多条重复要求合并；
- 编辑要求字段；
- 父子关系和来源继承；
- `created / edited / confirmed / split / merged` 全量留痕。

被拆分或合并的原要求标记为“已拆分/合并”，不会继续进入交付计划，但原文、来源和人工操作记录永久保留。

### 3.3 交付物、RACI 与倒排计划

人工确认后，系统按要求类型生成对应交付物，例如资格证明与核验清单、评分响应与得分证据、废标红线核验表、技术偏离响应表和商务报价依据。

每条确认要求生成 RACI：

- **R（Responsible）：** 实际执行人；
- **A（Accountable）：** 项目批准人；
- **C（Consulted）：** 法务或商务会签人；
- **I（Informed）：** 投标协同组。

系统从投标截止时间反推：内容交付、内部终审、签字盖章、终版锁定、正式递交。任务记录明确前置依赖；前置任务未完成时，后续节点不能被误标完成。

### 3.4 缺口泳道与红线

缺口自动分入五条泳道：

1. 材料缺失；
2. 能力缺口；
3. 证据不足；
4. 冲突待定；
5. 等待确认。

废标、无效响应、截止时间、签字、盖章、密封、格式和递交要求单独进入红线区。红线和截止要求仍需人工确认，系统不会仅凭模型输出形成正式结论。

### 3.5 报价计划

技术和商务要求会自动建立报价草稿，也支持手工增加报价项。系统保存数量、单位、单价、成本、税率、责任人和审批状态，并实时计算报价总额、估算成本和毛利率。演示数据明确标记为演示报价，不与真实商务结论混淆。

### 3.6 飞书与数字孪生闭环

作战任务同步飞书时使用稳定幂等键，相同任务重复同步不会重复创建。终审、签章、锁版和递交节点可进入飞书日历。回读飞书完成状态后，系统同步更新任务、交付物和要求状态。

数字孪生新增“作战执行”维度，公式为：

> 执行准备度 = 已完成正式任务数 ÷ 正式任务总数 × 100%

这个分数直接来自真实任务状态，不使用主观模型评分。数字孪生快照同时记录任务数量、完成数量和状态变化。

### 3.7 导出复用

作战图可导出 ZIP 工作包，包含：

- `01_要求目录.csv`
- `02_交付物.csv`
- `03_RACI责任矩阵.csv`
- `04_倒排计划.csv`
- `05_缺口清单.csv`
- `06_报价计划.csv`
- `feishu_bitable_rows.json`

这些文件均保留同一要求 ID，可复制到 Word，也可用于飞书多维表格导入或接口同步。

- 方向一、方向二、方向三的 Markdown 和 PDF 验收报告未修改。

## 九、已知边界与后续建议

当前版本已满足比赛演示和本地实际使用，但仍应保持以下边界意识：

1. 三份公开文档金标属于回归样本，不代表跨行业总体准确率；比赛后应扩展到至少 50 份完整招标文件。
2. 扫描件 OCR 目前采用明确兜底状态，尚未在本方向中引入新的 OCR 引擎；这避免了错误结构化，但会增加人工录入量。
3. RACI 的 A/C/I 默认使用角色占位，项目负责人应在正式投标前确认具体人员。
4. 演示报价是示例数据，正式报价仍需商务审批和财务口径确认。
5. 飞书真实同步依赖当前应用权限、可用成员 open_id 和日历配置；代码层已经通过伪客户端幂等与回写测试，实际发送前应在演示群执行一次非关键任务联调。
