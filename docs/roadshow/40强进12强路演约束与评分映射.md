## 2. 官方路演方法

本次培训给出的四个核心板块必须成为整套路演的骨架，逻辑接近“问题 → 行动 → 结果 → 意义”：

1. 问题值得解决。
2. AI 应用有深度。
3. 结果真实可信。
4. 方案可以复制。

表达顺序遵循两条规则：

- 先讲业务语言，再解释技术机制。
- 先给结论，再说明数据口径和适用边界。

时间结构确定为：

- 前 30 秒：提出一个具体、紧迫且与命题企业相关的问题。
- 中间 6 分钟：用同一个案例证明业务闭环、AI 深度、飞书协作、真实结果和复用性。
- 最后 30 秒：回到开场问题，给出一句可记住的结论。

官方 Skill 提供故事型、逻辑型和影响型三种结构。TenderTrace 当前适合采用“逻辑型主干 + 故事型开场”：评委背景混合、方案链路较复杂，需要按 Why → How → What → So What 推进；开场用真实投标角色和补充公告变化制造代入。影响型只有在人工基线与系统评测完成后才可采用，不能先写亮眼数字再补证据。

Skill 的逐字稿流程可用于生成初稿和复盘，但不能替代团队判断：输入需包含命题企业、7 分钟时长、分享者角色、场景材料和结构偏好；未核实信息统一标记为“待确认”；试讲后再按开场钩子、故事节奏、数字证据、技术可懂度、表达状态和答辩预判六个维度复盘。

## 3. 评分维度对项目的影响

### 3.0 两套口径如何一起使用

| 本届培训会议的五个关注面 | TenderTrace 的对应证据 | Skill 自检维度 |
|---|---|---|
| 业务价值 | 人工与系统基线、风险减少、决策与协作变化 | 业务提效与价值创造 30% |
| AI 应用创新性 | 与通用问答不同的要求账本、证据链和业务动作 | AI 技术创新深度 30% |
| AI 应用深度 | 多 Agent 进入核心拆标链路、分歧复核、失败恢复 | AI 技术创新深度 30% |
| 飞书 AI 能力应用深度 | 飞书内真实协作闭环，并明确所使用的飞书 AI 工具 | 不单列，需作为本届专项要求补充检查 |
| 方案专业度与现场表达 | 7 分钟闭环、证据、现场表现与 4 分钟答辩 | 展示专业度与成果完整性 20% |

Skill 另有“方案可推广性和影响力 20%”，它与培训反复强调的“方案能复制”一致，必须在结尾和答辩中明确。表中的百分比仅来自公开 Skill，不表述为本届组委会正式公布权重。

### 3.1 业务价值是最高优先级

产品不能只证明“能搜索”和“能生成报告”，还要证明它减少了什么风险、缩短了哪个环节、让哪类人更快作出什么决定。

当前可验证的结果包括：

- 自然语言需求进入后，系统能完成来源规划、采集、清洗、证据核验和 Word 输出。
- 定时订阅只推送新增内容，避免重复发送。
- 公告重大变化会使原投标决策失效并要求重新复核。
- 机会可以进入负责人、团队、关键人、任务、决策和复盘流程。
- 飞书任务、多维表格、日历和卡片操作具备幂等与回写机制。

比赛前需要补充的业务价值证据：

- 使用真实公开招标文件完成一次人工基线对照。
- 记录人工完成检索、拆标、分工所需时间，再与 TenderTrace 流程比较。
- 统计强制条款、截止时间、评分项、附件清单的识别准确率和召回率。
- 所有时间节省和准确率数据都保留样本、口径和原始记录，禁止根据感觉估算。

### 3.2 AI 深度必须出现在核心链路

AI 深度不能用 Agent 数量证明。评委需要看到：

- 不同 Agent 处理不同专业问题，而不是轮流生成文字。
- Agent 共享结构化状态，能够并行、合并、发现冲突并从 checkpoint 恢复。
- 每项结论带原文位置、置信度和状态。
- 低置信度、强制条款和 Agent 分歧进入人工复核。
- 模型不可用时，规则与本地检索仍能完成基础流程。

现有 TenderGraph、checkpoint、trace、证据链和模型网关可以支撑这套表达，但当前主图只有 `intent -> collect -> evidence -> report`。比赛前需要将智能拆标会审作为第二条领域工作流，而不是给现有四个节点更换 Agent 名称。

### 3.3 飞书能力需要形成业务动作

当前项目已经具备飞书机器人、多维表格、Task v2、日历、交互卡片、项目群、组织记忆和状态回写，这是较强基础。

路演中必须把这些接口组合成一个业务动作：选择机会后，一键创建投标战情室；拆标要求进入多维表格；责任人收到任务；截止日进入日历；群卡片完成认领、补证、确认和升级；结果回写 TenderTrace。

培训主持人明确表示：豆包工作伙伴不是强制绑定项，但本届口头要求至少使用一个飞书 AI 工具；同时建议突出豆包工作伙伴参与度，因为它与飞书生态和项目协作上下文结合更深。当前仓库未发现豆包、火山引擎或工作伙伴的实现与配置，因此：

- 不能在现阶段材料中声称已经接入豆包工作伙伴。
- 使用“效傲 X 分钟”Skill 打磨讲稿可以作为备赛过程证据，但不能自动等同于 TenderTrace 产品已使用飞书 AI 能力。
- 必须向 Coach 或赛区群确认：当前飞书机器人、Task、日历和多维表格是否满足赛道要求，还是还需在产品链路中接入明确的飞书 AI 工具。
- 如果需要产品级接入，应优先设计一个真实且小范围的入口，例如由豆包工作伙伴触发 TenderTrace 查询或读取机会简报，而不是只放品牌标识。

### 3.4 现场表达需要减少功能清单

7 分钟内展示五个并列卖点会削弱记忆。培训进一步明确“Demo 只证明一个关键闭环”，因此之前的五项产品能力继续保留，但路演压缩成同一业务闭环中的三个短演示片段：

1. 招标数字档案：一句需求形成持续更新、可追溯的机会档案，并出现一次真实公告变化。
2. 智能拆标会审：招标文件变成要求账本，多个 Agent 找出材料缺口和一项分歧。
3. 飞书投标战情室：要求账本变成成员任务、截止日和可回写的协作动作。

组织投标记忆作为结尾的“方案可复制”与持续学习证据，不单独占用一段长 GIF。16 个来源、365 项测试、证据核验和失败恢复作为可信支撑，不单独讲成产品功能。

## 4. 建议的 7 分钟故事线初稿

### 0:00 至 0:30 问题

使用一个服务器采购场景说明：团队并不只怕错过公告，更怕附件要求遗漏、补充公告改变截止日、多人协作状态不一致。开场数据必须来自后续真实基线测试，当前不填写未经验证的分钟数或百分比。

### 0:30 至 1:10 答案

用一屏说明 TenderTrace 如何把公开招标信息转化为可追溯、可执行的团队投标计划。只展示业务闭环，不展开技术架构。

### 1:10 至 2:20 演示高潮一

GIF 展示自然语言需求、来源规划、同一机会的公告与附件归并、原文证据和一次公告变化。最后停在“原决策失效，等待负责人复核”。

### 2:20 至 4:10 演示高潮二

GIF 展示公开招标文件进入智能拆标流程，形成资格、截止时间、评分、废标和附件要求。五个领域 Agent 写入同一要求账本，出现一项低置信度或冲突，人员完成确认。

### 4:10 至 5:25 演示高潮三

GIF 展示一键创建飞书投标战情室。要求同步到多维表格，法务、技术和商务任务进入 Task v2，截止日进入日历，成员在卡片上完成一次操作并回写 Web。

### 5:25 至 6:15 真实结果

展示人工基线与系统结果。遵循“先说变化、再说口径、最后解释意义”：

- 先说处理时间、漏项或任务建立过程发生了什么变化。
- 再说样本数量、文件类型、人工标注方法和测试环境。
- 最后说明这对投标负责人意味着什么。

没有完成真实测试前，PPT 只保留数据位置，不填写数字。

### 6:15 至 6:30 可复制性

说明来源适配器、要求类型、企业能力库和飞书协作模板如何配置到其他品类与组织。避免只说“可以推广”，需要给出复制所需的输入和边界。

### 6:30 至 7:00 结论

回到开场场景，说明 TenderTrace 已将一份不断变化的招标文件转化为团队可以执行和核验的投标计划。结尾不再增加新功能。

## 5. 项目优化优先级修正

结合评分权重和截止时间，开发顺序调整为：

1. 投标要求账本与五类高价值要求抽取。
2. 招标数字档案时间线与变化影响展示。
3. 拆标领域 Agent、冲突检测和人工复核。
4. 要求级飞书多维表格、Task v2、日历和卡片回写。
5. 真实基线测试、演示数据固定、GIF 录制与现场兜底。
6. 豆包工作伙伴参与方式在规则确认后插入，不先做无依据集成。
7. 企业能力库和组织记忆深化作为核心流程稳定后的增强项。

这一顺序与上一份方案相比，将“组织记忆深化”后移，将“真实效果测量”和“豆包工作伙伴口径确认”提升为比赛前的显式任务。

## 6. 答辩必须提前准备的五个问题

### 与通用大模型有什么区别

回答重点：权威来源采集、原文与附件证据、结构化要求账本、确定性工作流、飞书真实成员与任务回写。通用模型负责语言理解，TenderTrace 负责数据、状态、证据和业务动作。

### 如何处理 AI 幻觉

回答重点：原文位置、字段证据、置信度、规则降级、Agent 分歧、人工确认、已确认事实不可被模型覆盖。

### 数据如何统计

回答重点：每个数字必须说明样本、时间范围、来源、测试环境和计算方式。代理指标不能写成正式召回率。

### 方案如何复制

回答重点：说明新增一个来源、品类、企业能力库或飞书协作模板分别需要什么配置。不要只用“模块化”概括。

### 下一步迭代什么

回答重点：区分比赛前已完成、现场可验证、正在开发和赛后计划。智能拆标、豆包参与和组织学习的完成度必须与实际代码一致。

每题按“先结论、后证据、再边界”回答，控制在 30 至 60 秒。对未知项直接说明当前边界和下一步验证方式，不使用 Skill 示例中的虚构百分比、运行时长或客户案例。
