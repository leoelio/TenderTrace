# TenderTrace 一键飞书投标战情室优化进度与验收报告

**报告日期：** 2026年9月28日  
**独立验收对象：** 提升方向八——一键飞书投标战情室  
**产品界面名称：** 一键投标战情室  
**验收结论：** 软件功能与自动化闭环通过；真实双账号现场协作需在比赛使用的飞书租户内完成最终外部验收

## 一、验收结论摘要

本方向已完成从启动预检、资源编排、飞书协作、状态回写、冲突确认、公告变更增量推送到组织记忆归档的完整闭环。项目负责人可以在 TenderTrace 中确认进入执行，系统随后创建或复用项目卡片、主责任务、截止日历、多维表格和要求任务，并把每一步的资源标识、链接、执行次数、失败原因和重试结果写回项目详情页。

本次验收的核心结果如下：

- 页面形成七步协作时间线，从“确认进入执行”一直到“归档组织记忆”。
- 启动前同时检查应用身份、项目群、负责人、Bitable、Task v2、日历、执行数据和长连接。
- 同一项目连续启动三次，战情室主记录、步骤回执及外部资源标识保持稳定，没有重复生成同类记录。
- 某一步失败时可以只重试该步骤，成功步骤及原资源标识保持不变。
- 飞书任务完成与本地人工状态不一致时进入确认队列，不自动覆盖人工结论。
- 公告变更只发送负责人已经确认的受影响行动，未确认和不受影响对象不会被批量推送。
- 项目结束后可归档到当前组织空间，保留权限边界、项目关联和执行回执。
- 数字孪生档案已统计战情室资源，并记录重试、回写、增量推送和归档事件。
- 全项目回归通过：506项测试通过、552项子测试通过、0项失败。
- 本地服务、首页、前端脚本、战情室接口和长连接监听器均通过运行验证。

## 二、原问题与本次解决目标

此前系统能够分析项目、生成要求、任务与判断，但“分析完成”到“团队真正开始协作”之间仍需要人工搬运：负责人需要手工建群、复制要求、创建任务、安排日历、维护多维表格，再把执行状态带回系统。这会导致重复创建、编号不一致、截止时间不同步、变更通知范围过大及执行结果难以审计。

本次优化解决以下问题：

1. 启动前能否明确知道还缺少哪些账号、权限、人员和数据？
2. 能否一次创建真实协作资源，并在重复操作时自动复用？
3. 单个资源创建失败后，能否独立恢复而不重建其他成功资源？
4. 飞书中的任务状态能否安全回写，并保护本地人工判断？
5. 公告更正后，能否只通知真正受影响且已确认的行动？
6. 项目结束后，能否将执行过程沉淀为有空间权限的组织记忆？

## 三、完整业务流程与界面设计

### 3.1 七步时间线

页面按实际业务顺序展示以下七步：

1. **确认进入执行：** 未确认前只展示计划，不创建飞书外部资源。
2. **身份与权限预检：** 核查应用身份、群、负责人、Bitable、Task v2、日历、要求数据和监听器。
3. **编排协作资源：** 创建或复用项目总览卡片、主责任务、截止日历、多维表格和要求任务。
4. **团队协同执行：** 团队在飞书处理任务和会审内容，TenderTrace 保存资源关系。
5. **状态回写确认：** 读取飞书任务结果；存在人工状态冲突时进入确认队列。
6. **变更增量推送：** 只发送最新公告变更中已由负责人确认的受影响行动。
7. **归档组织记忆：** 将项目回执归档到绑定的组织协作空间。

### 3.2 页面结构

项目详情页新增完整的战情室指挥界面：

- 顶部显示协作状态、启动次数和资源复用说明。
- 七步横向流程展示当前进度、注意项和完成状态。
- 启动预检以卡片矩阵显示八项检查结果。
- 协作资源区展示群消息、任务、日历和多维表格的真实回执与打开链接。
- 执行回执区显示每一步的状态、尝试次数、是否复用、错误原因和单步重试按钮。
- 状态回流区显示监听器、最近同步、失败步骤和待确认冲突数。
- 增量变更区显示最新轮次、已确认行动、待确认行动和失败回执。
- 页面提供“回读团队状态”“发送已确认变更”“归档组织记忆”和“刷新回执”操作。

页面采用深蓝指挥台、青色状态线和分层卡片设计，并适配窄屏。产品界面没有出现“方向八”等内部研发编号。

## 四、已完成的技术措施

### 4.1 数据模型与持久化回执

数据库模式升级到45，新增三类数据：

- `feishu_war_rooms`：一项目一战情室，保存组织空间、飞书接收群、状态、启动次数、最近成功与同步时间及归档记忆。
- `feishu_war_room_steps`：保存步骤状态、幂等键、资源类型、资源标识、资源链接、复用标记、尝试次数、错误和回执。
- `feishu_war_room_sync_events`：保存启动、重试、状态回写、变更推送和归档的方向、状态、操作者与载荷。

### 4.2 幂等与重复启动保护

战情室编号由项目编号稳定生成；每一步的幂等键由“项目 + 步骤”稳定生成。数据库对项目战情室及战情室步骤设置唯一约束。外部任务和日历继续使用原有幂等令牌。

连续三次启动的自动化与演示验收结果表明：

- 战情室主记录未增加重复项。
- 步骤回执数量保持不变。
- 项目卡片、主责任务、截止日历和多维表格资源标识保持一致。
- 启动次数及步骤尝试次数正确累加，并明确标记“已复用”。

### 4.3 可独立恢复的失败步骤

每个步骤单独保存成功或失败。失败步骤可以通过独立接口重试，重试不会调用无关步骤。即使单步重试再次失败，系统也会保存新的失败回执和错误详情，同时保留此前已成功创建的资源标识，避免资源链接丢失。

### 4.4 Web与飞书状态映射

系统可回读要求任务和履约作战任务。对要求任务采用保守冲突策略：当飞书显示完成、但本地仍是人工维护中的状态时，系统只更新飞书状态并记录冲突事件，不将本地要求直接改为完成。负责人可以据此核对交付物后再确认。

### 4.5 变更增量推送

系统读取最新公告变更冲击轮次，只选择状态为“已确认”的行动进行推送。每个行动分别记录群消息、任务和日历渠道状态，并复用已有幂等键。测试和演示均验证未确认行动不会被发送。

### 4.6 多维表格链接与资源回查

多维表格资源回执同时保存 Base App Token 与 Table ID，并生成可直接打开对应数据表的链接。群消息链接包含群和消息标识；任务、日历也提供对应飞书入口。

### 4.7 数字孪生和组织记忆

数字项目档案新增战情室资源数和失败步骤数，战情室数据也进入状态指纹。重试、团队状态回写、增量推送及归档都写入项目时间线。归档操作要求战情室已经绑定组织空间，生成的组织记忆保留项目编号和证据来源，避免跨空间误读。

## 五、演示验收案例

### 5.1 演示项目

- 项目名称：政务云一键投标战情室
- 项目编号：TT-WR-20260928
- 本地地址：`http://127.0.0.1:8000/?opportunity=demo-feishu-war-room`
- 组织空间：政务云投标战情室（双账号演示）
- 协作身份：李经理（脱敏）、周工（脱敏）
- 要求账本：3条
- 七步流程：7步
- 持久化步骤回执：6份

### 5.2 失败恢复案例

第一次启动时，演示要求任务同步返回部分失败，战情室整体状态为“部分就绪”。随后只重试“要求账本任务”步骤，该步骤恢复成功；项目卡片、主责任务、截止日历及多维表格没有重新创建。之后再次启动两次，最终累计启动三次且回执主键和资源标识不重复。

### 5.3 状态冲突案例

飞书要求任务显示完成，而 TenderTrace 中对应要求仍处于人工处理中。状态回读后：

- 飞书任务状态更新为完成。
- 本地人工业务状态保持处理中。
- 系统生成1条待确认冲突。
- 项目数字孪生时间线记录本次回写。

### 5.4 公告变更案例

演示项目的投标截止时间发生更正，系统生成受影响行动。负责人核对来源后确认其中一项，战情室只发送该已确认行动，消息与任务渠道均返回成功；未确认行动没有被发送。

### 5.5 归档案例

项目结束后，战情室归档到绑定的组织空间，生成一条关联当前项目的经验记忆，并将战情室状态更新为“已归档”。

## 八、真实飞书连接与双账号验收边界

当前本机飞书基础条件已经满足：配置开关开启，消息应用凭证存在，默认接收群存在，Bitable 和日历目标已配置，官方长连接监听器处于运行状态。这说明 TenderTrace 具备调用和接收飞书事件的本地条件。

本报告中的双账号案例使用两个脱敏协作身份和确定性飞书客户端完成，目的是稳定验证状态机、幂等、回执、冲突及增量推送。案例中的演示资源ID属于验收样本，不能被表述为两个真人已经在真实飞书客户端逐项完成操作。

最终现场验收建议使用比赛租户执行一次以下动作：

1. 两个真实账号加入同一项目群，并确认应用可见范围覆盖两人。
2. 账号A启动战情室，确认群卡片、任务、日历和Bitable可打开。
3. 账号B完成一项要求任务并补充证据。
4. 回到 TenderTrace 点击“回读团队状态”，核对回写结果。
5. 修改一条演示公告，负责人确认一项受影响行动并发送。
6. 连续点击启动三次，确认飞书端没有出现重复资源。

完成上述现场操作后，真实双账号验收项即可由“待现场确认”更新为“通过”。

## 十、比赛演示建议

建议采用以下3分钟流程：

1. 打开演示项目，先展示八项预检和七步流程。
2. 展示已创建的群卡片、主责任务、截止日历和Bitable资源。

4. 展示要求任务的重试次数，说明单步恢复不会重建其他资源。
5. 点击“回读团队状态”，解释人工状态冲突不会被系统覆盖。
6. 展示公告更正轮次，只发送负责人确认的受影响行动。
7. 以“归档组织记忆”结束，说明经验可以在同一组织空间内复用。

评委追问“如何避免重复和误覆盖”时，可直接回答：每个项目和步骤都有稳定幂等键；每一步有独立回执；飞书完成状态与本地人工状态冲突时进入确认队列；公告变更必须由负责人确认后才推送。

## 十一、遗留事项与后续建议

本方向的软件实现、自动化闭环和本地运行已达到验收要求。剩余事项只涉及外部真实环境：

1. 在比赛使用的飞书租户完成两个真人账号的六步现场验证。
2. 核对应用发布版本的 Task v2、日历、消息和Bitable权限覆盖范围。
3. 将真实项目群绑定到组织空间，避免演示群与正式群混用。
4. 现场测试一次断网或权限撤销后的单步失败与恢复。

这些事项不影响本地功能与演示样本运行，但真实双账号验收完成前，不应宣称外部协作链路已经百分之百完成。
