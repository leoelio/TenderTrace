# TenderTrace 路演竞争点与项目优化方案

更新日期：2026-09-03

## 1. 审视结论

TenderTrace 当前的主要问题不是功能数量少，而是功能之间缺少一个对评委可见的核心业务对象。采集、证据、机会、公告变更、团队、飞书任务和组织记忆都已存在，但目前分别分布在不同页面和流程中，容易被理解为一组招投标工具。

路演不应把“多源搜索”和“公告变更”单独包装成两个主卖点。它们属于底层能力，应共同支撑一个更完整、更有记忆点的产品概念：

> 为每一个招标机会建立一份持续变化的数字档案，并把这份档案转化为团队可执行、可追溯的投标作战计划。

建议形成五个明确竞争点，其中前四个作为路演主展示，第五个作为产品壁垒与闭环展示。

## 2. 竞争点一：活的招标数字档案

### 评委能听懂的一句话

> 它不是一条搜索结果，而是一份会随着公告、附件和团队决策持续更新的招标数字档案。

### 现有项目基础

- 16 个公开、登录态和国际来源适配器。
- 跨来源清洗、去重、附件快照和原文证据。
- `notice_revisions` 保存公告前后版本和变化字段。
- 重大变化会使既有 Go/Hold/No-Go 决策失效，并进入负责人复核。
- 机会详情已包含负责人、团队、关键人、事实核验、关系行动和结果复盘。

### 需要优化的内容

- 将同一招标的公告、补充公告、结果公告和附件组织成统一时间线。
- 增加“变化影响图”：变化了什么、影响哪些要求、任务、截止日和决策。
- 在一屏内呈现当前有效事实、历史版本、来源证据和团队动作。
- 为跨来源关联增加人工合并/拆分入口，避免错误聚类不可纠正。

### 实现难度与效果

- 难度：中。
- 原因：版本记录、事实核验和决策失效已经实现，主要工作是统一领域模型、关联规则和可视化。
- 预期效果：高。时间线、字段前后对比和决策失效非常适合 GIF，评委能立即看懂“系统在持续盯标”。

### PPT 展示标题

> 一条公告只是开始，TenderTrace 为每个机会维护一份持续更新的数字档案

## 3. 竞争点二：智能拆标作战图

### 评委能听懂的一句话

> 系统把几十页招标文件拆成资格、技术、商务、评分、格式和附件任务，并告诉团队还缺什么。

### 现有项目基础

- PDF、DOCX、XLSX 附件下载和文本抽取。
- 事实字段、证据摘录、机会评分和销售准入门禁。
- 负责人、协作团队、角色、任务和截止时间模型。
- 当前已有需求维度检查，但只判断正文是否出现相关关键词，尚未形成逐条要求账本。

### 需要新增和拓展的内容

1. 建立“投标要求账本”，每行保存要求编号、类型、强制性、评分权重、原文位置、置信度和状态。
2. 把招标公告、招标文件、评分办法、技术清单、合同和补充文件放入同一个文件树。
3. 自动识别资格门槛、废标条款、技术参数、评分项、签章格式、附件清单和全部截止时间。
4. 建立企业能力库，保存资质、产品参数、项目案例、人员证书和合作伙伴能力。
5. 将每条招标要求与企业能力证据匹配，分为“已满足、待补证、存在差距、必须确认”。
6. 从要求账本生成投标目录、责任分工、倒排计划和 Bid/No-Bid 输入，但不直接替用户作最终承诺。
7. 对扫描件、表格和跨附件引用保留降级与人工补录路径。

### 实现难度与效果

- 难度：高。
- 原因：需要新增数据库表、文档分块、结构化抽取、证据定位、人工编辑、能力库和一组 API/UI；这是实质性新功能，不是页面包装。
- 可控方式：第一版只覆盖资格、截止时间、评分项、废标条款和附件清单五类高价值要求，用 3 套公开招标文件建立人工标注集。
- 预期效果：最高。这会把项目从“招标聚合器”提升为“投标准备工作台”，也是最值得投入的核心竞争点。

### PPT 展示标题

> 一份招标文件，自动变成有证据、有负责人、有截止时间的投标作战图

## 4. 竞争点三：可质询的多智能体会审

### 评委能听懂的一句话

> 多个 Agent 不负责轮流聊天，而是从不同专业角度审查同一条要求，并把分歧交给人确认。

### 现有项目基础

- TenderGraph 已支持节点、事件、checkpoint、失败记录和恢复。
- 当前采集主图是 `intent -> collect -> evidence -> report`。
- 已有规则、本地模型和云端模型三种模式，以及结构化模型网关。
- Agent 评测页面已经能显示 checkpoint、trace 和证据通过情况。

### 需要新增和拓展的内容

- 文书结构 Agent：识别文件关系、章节、附件、截止日和评审办法。
- 合规 Agent：识别资格门槛、废标条款、签章、格式和提交要求。
- 技术匹配 Agent：比较技术参数与企业产品、案例和人员能力。
- 商务研判 Agent：评估预算、交付周期、竞争态势和投入产出。
- 证据审计 Agent：检查每条结论是否有原文位置，识别相互冲突和低置信度结果。
- 汇总节点只合并一致事实；Agent 分歧、强制条款和低置信度内容进入人工复核。
- 人工确认结果具有更高优先级，后续运行不得自动覆盖。

### 实现难度与效果

- 难度：中高，依赖“智能拆标作战图”的要求账本。
- 原因：无需引入第二套 Agent 框架，现有 TenderGraph 足以承载；主要工作是定义节点输入输出、分歧规则和复核状态。
- 预期效果：高。Agent 并行处理、结论汇合、冲突变红、人工确认是一段非常直观的动态演示，也能避免“为了多智能体而多智能体”的质疑。

### PPT 展示标题

> Agent 可以犯错，但每个分歧、置信度和原文依据都必须接受质询

## 5. 竞争点四：飞书原生投标战情室

### 评委能听懂的一句话

> 发现机会后不再跳到另一个项目管理工具，团队直接在飞书里完成分工、复核、催办和决策。

### 现有项目基础

- 已能读取机器人所在群和授权成员，并使用真实 `open_id`。
- 已能创建项目群、邀请成员、发送交互卡片和处理卡片回调。
- 已有多维表格、Task v2、日历、晨报、升级提醒和状态回写。
- 已有唯一负责人、阶段化团队、客户关键人、关系行动和 Go/Hold/No-Go 动作契约。
- 飞书群已能形成隔离的组织记忆空间。

### 需要优化的内容

1. 增加“一键创建投标战情室”，一次完成项目群、要求账本、任务和日程初始化。
2. 将智能拆标产生的强制要求和材料缺口同步到多维表格，而不只是同步公告。
3. 按要求责任人创建 Task v2；法务、技术、商务和伙伴拥有不同的默认任务视图。
4. 群卡片提供认领、补证、退回、确认、完成和升级操作，并双向回写 Web 与 SQLite。
5. 截止日变化时自动调整相关任务并要求负责人确认，不静默覆盖人工安排。
6. 路演环境提供连接预检和失败兜底，外网或飞书权限异常时仍能展示最近一次真实同步证据。

### 实现难度与效果

- 难度：中。
- 原因：大部分飞书接口和幂等机制已存在，核心工作是把“公告级协作”下沉到“要求级协作”。
- 预期效果：最高。它同时满足飞书赛道要求和真实团队场景，能够明显区别于只发送机器人消息的项目。

### PPT 展示标题

> 飞书不是消息出口，而是整场投标工作的执行现场

## 6. 竞争点五：会成长的组织投标记忆

### 评委能听懂的一句话

> 每次搜索、判断、客户反馈和投标结果，都会让系统下一次更懂这家公司该投什么、缺什么、为什么会赢或输。

### 现有项目基础

- 个人记忆已经记录查询、点击、下载、订阅和运行行为。
- 组织记忆按飞书项目群隔离，可记录决策、客户信号、竞品、风险和经验。
- 组织记忆可以审计式转换为机会事实或客户行动。
- 中标/失标复盘已能回流胜率、败因、竞争对手和成交价格样本。
- 记忆建议可被采纳、忽略，并创建真实订阅或业务动作。

### 需要优化的内容

- 将零散记忆升级为企业能力库和投标知识图谱：客户、品类、区域、产品、资质、案例、伙伴、竞品和历史结果形成关系。
- 新机会进入时，自动给出“为什么适合我们、可复用哪些案例、还缺哪些证明、与哪次失败相似”。
- 区分事实、推断和建议，并显示样本数量；样本不足时不生成伪精确胜率。
- 让成员在飞书群中确认或纠正记忆，保留来源和修改历史。

### 实现难度与效果

- 难度：中高。
- 原因：记忆、复盘和市场上下文已经存在，但需要新的实体关系、能力库和匹配策略。
- 预期效果：中高。长期产品壁垒强，但短期视觉冲击弱于拆标和飞书战情室；适合用作路演闭环与未来价值，不应抢占最多演示时间。

### PPT 展示标题

> 每完成一次投标，下一次判断就多一份属于企业自己的经验

## 7. 支撑层，不单独作为主卖点

以下能力非常重要，但建议作为每张功能页的可信性标识或单独一页工程证明，不再占用主故事位置：

- 16 个来源与地区范围路由。
- 原文证据、附件快照和字段核验。
- 本地优先检索与模型失败降级。
- checkpoint、trace、失败恢复和幂等同步。
- 365 项 Python 测试、456 项子测试和 34 项验收检查。
- 敏感配置、登录态和飞书身份边界。

## 8. 实施优先级

### 第一阶段：用现有能力快速形成可见差异

1. 重构机会详情为“招标数字档案”，加入统一时间线和变化影响区。
2. 将飞书已有的项目群、任务、日历和卡片能力收束为“一键创建投标战情室”。
3. 建立一套服务器采购的稳定公开演示数据，保留全部原文和运行证据。

验收：数字档案能展示公告、附件、事实、变化、决策和行动；重大变化可触发决策失效；战情室初始化幂等且三端状态一致。

### 第二阶段：开发真正的新核心功能

1. 建立投标要求账本和人工编辑界面。
2. 先完成五类要求抽取和证据定位。
3. 接入企业能力证据匹配、责任分工和倒排计划。

验收：3 套人工标注招标文件分别统计强制项、截止日、评分项、废标条款和附件清单的准确率与召回率；所有结论能定位到文件和页码/章节。

### 第三阶段：让多智能体和飞书围绕要求账本工作

1. 增加五个领域 Agent 节点和分歧复核机制。
2. 将要求行同步飞书多维表格和 Task v2。
3. 完成卡片操作、任务状态和人工确认的双向回写。

验收：低置信度和 Agent 冲突稳定进入复核；人工确认不被覆盖；重复同步不产生重复任务；失败可从 checkpoint 恢复。

### 第四阶段：形成组织学习闭环

1. 建立企业能力库和实体关系。
2. 把中标/失标、客户反馈和要求完成情况回流匹配策略。
3. 在新机会中展示可复用案例、相似失败和证据缺口。

验收：每条推荐显示来源、样本数和解释；组织之间数据隔离；样本不足明确降级。

## 9. 路演展示结构

主线使用同一个“服务器采购”案例，避免每页更换场景：

1. 一句话提出服务器采购需求，形成招标数字档案。
2. 新补充公告改变截止时间，系统展示影响并使旧决策失效。
3. 打开招标文件，生成投标作战图和材料缺口。
4. 五个 Agent 会审，展示一项冲突及人工确认。
5. 一键创建飞书战情室，要求变成成员任务和日历。
6. 投标结果与复盘回流组织记忆，为下一次机会提供依据。

三个演示片段分别使用一张 8 至 15 秒 GIF：数字档案与公告变化一张、要求账本与多 Agent 会审一张、飞书战情室一张。三张 GIF 必须属于同一个服务器采购闭环，不能被讲成三个彼此独立的功能。组织记忆使用静态关系图或短前后对比，不再增加持续运动画面。最后保留一次评委随机输入的短现场验证，证明系统不是固定录屏或硬编码。

## 10. 最终推荐

比赛前最值得投入的不是继续扩充来源，也不是重写 Agent 框架，而是完成以下组合：

> 活的招标数字档案 + 智能拆标作战图 + 可质询的多智能体会审 + 飞书原生投标战情室。

这四项有明确依赖关系，也都能从现有项目延伸出来。数字档案和飞书战情室能够较快形成效果；智能拆标是难度最高但价值最大的新增核心；多智能体建立在拆标账本之上，能够用现有 TenderGraph 实现。组织投标记忆作为第五项闭环能力，适合在核心链路稳定后继续深化。
