## 一、目标与验收口径

本方向解决“企业究竟凭什么能满足这条招标要求”的问题。系统把资质、产品参数、人员、案例、交付服务和伙伴授权建立为可复用且可核验的企业能力护照，再逐条对照已确认的招标要求。系统不输出虚假的精确匹配百分比，而是使用五种可解释结果：**有据满足、明确缺口、证据不足、存在冲突、待人工确认**。

验收成功标准如下：

1. 六类能力证据均能录入、核验、版本化和复用。
2. 每条能力保存适用主体、型号、地区、有效期、授权范围、来源文件与确认状态。
3. 要求与能力支持多对多匹配，并同时保留要求 ID、能力 ID、能力版本 ID 和项目快照 ID。
4. 主体、型号、地区、有效期和授权范围先由确定规则核验，模型只提出语义候选。
5. 不同主体、不同型号和过期证书不得合并为同一项有效能力；关键能力不得由模型自动确认。
6. 明确缺口可以一键转为补充材料、内部确认、伙伴协同或放弃要求任务。
7. 缺口任务进入正式作战计划，完成状态回流数字孪生；项目结果回流企业能力护照。
8. 项目使用能力时保留当时版本，后续能力更新或证书过期会触发复核。
9. 页面以“要求树—匹配矩阵—能力护照”三栏展示，并单列风险预警、缺口行动和相似案例。

## 二、最终设计

页面采用三栏能力驾驶舱：

| 区域 | 展示内容 | 评委能看见的证据 |
|---|---|---|
| 左栏：招标要求树 | 要求编号、标题、来源定位 | 结论对应哪一条原文要求 |
| 中栏：逐项匹配矩阵 | 五态结论、规则原因、置信度、人工确认 | 为什么满足、为什么冲突、谁确认 |
| 右栏：企业能力护照 | 六类证据、主体、型号、地区、版本、状态 | 企业凭什么满足、证据当前是否有效 |
| 风险预警条 | 到期、主体缺失、型号冲突、授权范围不足 | 关键风险不会藏在普通列表中 |
| 缺口行动闭环 | 补材料、内部确认、伙伴协同、放弃要求 | 缺口怎样变成可执行任务 |
| 相似案例 | 行业、地区、金额、型号、结果、样本数 | 案例为何相似及其样本边界 |

桌面端三栏并排，窄屏自动变成单栏。状态使用颜色和文字双重编码，避免仅靠颜色判断。

## 三、功能交付清单

### 3.1 六类企业能力护照

已支持：产品参数、资质证书、人员能力、交付服务、项目案例、合作伙伴授权。每条能力均保存：

- 唯一能力编号和名称；
- 适用主体；
- 产品型号；
- 适用地区；
- 有效起止日期；
- 授权范围；
- 来源文件、来源链接和原文定位；
- 核验状态、负责人、行业、脱敏标识；
- 内容哈希、版本号、创建人和更新时间。

任何关键字段变化都会生成新版本。已确认项目仍保留原项目快照，新的能力版本不会静默覆盖原判断。

### 3.2 多对多匹配与五态结论

已确认的招标要求会与当前工作空间的已核验能力进行多对多匹配。每条匹配同时保存：

- `requirement_id`：招标要求；
- `capability_id`：企业能力；
- `capability_version_id`：使用的能力版本；
- `project_snapshot_id`：该项目的固定快照；
- 规则核验明细、冲突代码、建议置信度和原因；
- 人工结论、确认人、确认说明和确认时间。

五态分别为：

| 结论 | 使用条件 |
|---|---|
| 有据满足 | 有要求原文、企业证据、版本快照且经人工确认 |
| 明确缺口 | 地区或确定条件明确不覆盖 |
| 证据不足 | 类别关系、授权范围或关键材料不足 |
| 存在冲突 | 型号不一致、证书过期等硬冲突 |
| 待人工确认 | 确定字段未发现硬冲突，但语义对应仍需负责人确认 |

### 3.3 确定规则优先与防误拼接

已实现以下规则护栏：

1. 证书过期：直接判为冲突，已确认匹配转为待复核。
2. 地区超出授权范围：判为明确缺口。
3. 招标明确型号而企业证据为相近型号：判为型号冲突，禁止自动拼接。
4. 伙伴授权没有授权范围：判为证据不足。
5. 要求类别与能力类别不相容：判为证据不足。
6. 招标原文与企业证据明确指向同一型号：可形成“有据满足”建议，但仍需人工确认。

模型只能引用已提供的能力 ID。它不能创造证书、案例、型号或来源，也不能覆盖人工确认结论。

### 3.4 能力版本、项目快照与审计

能力字段变化会增加版本号并保存完整快照。项目匹配时生成固定项目快照；人工确认后，快照记录确认人和时间。公告变化、能力更新或证书过期时，原“人工已确认”状态会转为“待复核”，而不是继续显示为有效。

审计事件覆盖：能力创建、能力更新、证书失效、匹配确认、缺口行动创建和缺口行动完成。

### 3.5 缺口行动闭环

非“有据满足”的匹配可直接转换为四类行动：

- 补充材料；
- 内部确认；
- 伙伴协同；
- 放弃要求。

创建行动时，系统同时生成 `capability_gap` 类型的正式作战任务，沿用同一要求 ID。该任务能进入方向四的履约作战图，也能复用现有飞书任务同步。任务完成后，缺口行动状态、作战计划完成度和数字孪生计数同步更新。

### 3.6 相似案例与结果回流

项目中标或未中标结果可回流至已确认能力，形成能力履约记录。相似案例按地区、金额、型号、行业和结果计算可解释排序，并显示命中维度和样本数。演示样本均标记为脱敏，避免把演示数据与真实客户数据混用。

### 3.7 工作空间隔离

能力护照按组织工作空间读取和匹配。项目会绑定一个能力工作空间，分析时仅使用该空间的能力资料。专项测试验证两个工作空间的能力互不可见。

本方向采用增量数据表和兼容字段，不另建第二套机会或要求系统。

回归结论：

- 原 `product / qualification / delivery / case` 能力类型继续兼容；

- 缺口任务使用独立 `capability_gap` 里程碑类型，不覆盖原交付任务；
- 原公告变化复核机制继续工作，并扩展到能力更新和证书过期；
- 全量 491 项测试与 534 个子测试通过，未发现方向一至方向四功能损失；
- 方向一至方向四的 Markdown 和 PDF 验收报告未修改。

## 九、已知边界与后续建议

1. 当前相似案例为 3 个脱敏演示样本，页面明确显示样本数；正式比赛不应把小样本排序解释为统计预测。
