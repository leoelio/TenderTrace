# TenderTrace GitHub 项目融合调研与实施优先级

调研日期：2026-09-03

## 一、结论先行

TenderTrace 当前并不缺功能数量。16 个数据源、证据链、机会经营、团队协作、组织记忆和飞书联动已经构成了较宽的能力面。真正影响比赛表达的是：各能力还没有全部收束到一个让评委一眼看懂、能现场操作、能产生明确业务结果的主闭环。

建议把产品主线升级为：

> **从“发现招标”到“完成投标准备”的证据化协同工作台。**

路演只演示一条完整链路：捕捉招标公告与附件 -> 自动拆解招标文件 -> 生成合规矩阵 -> 多智能体会审 -> 飞书分工与催办 -> 形成 Go/Hold/No-Go 决策及可追溯报告。

这条链路能够同时承接项目现有的四个重点：招投标文书捕捉、群员协作、多智能体、飞书融合，又能避免继续堆砌彼此孤立的工具。

## 二、候选项目筛选

### 1. amgdy/rfp-analyzer：优先借鉴

- 仓库：https://github.com/amgdy/rfp-analyzer
- 许可：MIT
- 调研时状态：6 stars，83 个代码/配置文件，15 个测试文件，README 声明 323 项测试。
- 有价值的机制：从 RFP 提取评分条件；按条件评价多个响应文件；为每项输出置信度；低置信度自动二次分析；长文档分块后合并；在正式评分前让用户确认评分条件和权重。
- 不宜照搬的部分：整体强依赖 Azure OpenAI、Azure Document Intelligence、Blob Storage 和 Streamlit，与 TenderTrace 的本地优先架构不一致。
- 融合方式：只吸收“结构化条件模型、置信度、复核门禁和长文档分块策略”，在 TenderTrace 现有 FastAPI、SQLite、附件抽取和模型网关上重新实现，不引入 Azure 基础设施。

### 2. twinturbosystems/govcon-starter-harness：优先借鉴

- 仓库：https://github.com/twinturbosystems/govcon-starter-harness
- 许可：MIT
- 调研时状态：0 stars，26 个文件，属于刚形成但领域结构清晰的小项目。
- 有价值的机制：Bid/No-Bid 加权量表；按来源章节建立稳定需求编号；把投标说明、评审因素、工作任务、附件、格式和截止时间交叉映射；给每项需求指定卷册、章节、负责人、截止日和状态；所有缺口置顶，而不是藏在报告末尾。
- 不宜照搬的部分：规则面向美国联邦采购，包含 FAR、SAM、NAICS 等专有概念；主要是提示词和 Markdown 工作流，不是完整产品代码。
- 融合方式：将它的“合规矩阵方法”本地化为中国招投标字段，并连接 TenderTrace 已有的机会负责人、团队角色、Task v2、日历和审计事件。

### 3. open-contracting/cardinal-rs：选择性借鉴

- 仓库：https://github.com/open-contracting/cardinal-rs
- 许可：MIT
- 调研时状态：14 stars，246 个文件，128 个测试相关文件，仍在维护。
- 有价值的机制：用确定性规则计算公共采购异常指标，而不是让模型凭感觉下结论。例如投标准备期过短、单一投标人、投标价格异常接近、最低价异常淘汰、废标比例异常等；每个指标都有公式、阈值、解释和测试样例。
- 不宜照搬的部分：核心实现为 Rust，且许多指标依赖完整 OCDS 投标/中标数据；TenderTrace 的国内来源不一定都有足够字段。
- 融合方式：第一期只实现数据充足的指标，例如投标窗口过短、同一采购人供应商集中度、公告重大变更和异常低价线索。产品中统一称“需复核信号”，不能直接定性为围标、串标或腐败。

### 4. samshad/public-tender-analysis-dashboard：第二阶段借鉴

- 仓库：https://github.com/samshad/public-tender-analysis-dashboard
- 许可：MIT
- 调研时状态：0 stars，35 个文件，无自动化测试，最后实质更新较早。
- 有价值的机制：采购主体与供应商名称归一化；采购主体聚类；BERTopic 主题发现；采购主题随时间变化；供应商中标次数和金额集中度的联动钻取。
- 不宜照搬的部分：代码绑定 Nova Scotia 固定数据列和 Dash 页面，主题模型在页面回调中现场训练，性能和工程质量不适合直接合并。
- 融合方式：只借鉴分析口径，在 TenderTrace 本地库上离线生成“品类趋势、采购人画像、供应商集中度”快照，再由现有 Web 页面和飞书晨报展示。

### 5. aadrikasingh/AI-Powered-RFP-Analyzer：仅作角色参考

- 仓库：https://github.com/aadrikasingh/AI-Powered-RFP-Analyzer
- 许可：MIT
- 调研时状态：8 stars，40 个文件，无自动化测试。
- 有价值的机制：把合规、法律风险、供应商、市场和谈判策略拆成不同分析角色，再汇总为统一评价。
- 不宜照搬的部分：依赖 Azure AI Search、Azure Document Intelligence 和多个云模型，示例数据和模拟能力较多，测试不足。
- 融合方式：参考角色边界，不复制它的云端架构和实现。

## 三、明确排除

- `kakssjs/toubiaojuece`、`HarleyCoops/WorkspaceAlberta`：功能叙述有参考价值，但仓库未声明许可证，不能复制或融合源码。
- `ZainAhmed9/bidengine-ai-showcase`：只公开展示内容，源码私有。
- Dify、Flowise、CrewAI、AutoGen 等通用平台：规模过大，会引入新的运行时和认知负担；TenderTrace 已有图编排、checkpoint、trace 和模型网关，没有必要为了“看起来多智能体”重写底座。
- Docling、MinerU 等大型文档平台：可作为后期可选抽取后端，但不应该成为比赛前的主改动。当前应先把“抽取结果如何驱动投标协作”做深。

## 四、推荐融合后的产品结构

### 核心竞争点：智能拆标舱

用户从已捕捉的机会进入拆标舱，也可以补充上传招标文件及附件。系统生成统一的“投标要求账本”：

| 字段 | 作用 |
|---|---|
| 需求编号 | 与原文章节或页码稳定绑定，支持追溯 |
| 原文证据 | 原文片段、文件名、页码/章节和链接 |
| 类型 | 资格、技术、商务、评分、格式、附件、截止时间 |
| 强制性 | 区分废标风险项和一般响应项 |
| 评分权重 | 记录明示权重；原文未说明时不得猜测 |
| 负责人 | 连接机会团队和飞书真实成员 |
| 截止时间 | 连接 Task v2 与日历提醒 |
| 证据材料 | 关联企业资质、案例、人员和待补材料 |
| 状态 | 待确认、待分配、准备中、待复核、已完成 |

这不是单独的“PDF 分析工具”，而是后续多智能体和团队协作共同读写的业务底座。

### 多智能体会审

保留 TenderGraph，不引入第二套 Agent 框架。新增领域节点：

1. 文书结构 Agent：识别文件、章节、附件、截止时间和评审办法。
2. 合规 Agent：抽取资格条件、废标条款、签章/格式要求，生成合规矩阵。
3. 技术匹配 Agent：把技术参数与企业能力、案例和人员证据进行匹配。
4. 商务研判 Agent：评估预算、周期、竞争态势和 Bid/No-Bid 因素。
5. 证据审计 Agent：检查每个结论是否有原文依据，标记冲突、缺失和低置信度项。

每个 Agent 只输出结构化事实和建议，不直接覆盖人工确认结果。低置信度、Agent 分歧、强制条款和重大公告变更必须进入人工复核队列。

### 飞书投标战情室

将已有飞书能力从“能发消息、能建任务”收束为一次可见的项目动作：

1. 点击“创建投标战情室”。
2. 自动创建/绑定项目群和多维表格要求账本。
3. 按要求负责人创建 Task v2，强制项和临期项自动提醒。
4. 群卡片可执行认领、确认、退回补证、完成和升级。
5. 任何动作回写 Web、SQLite、审计记录和机会准入状态。

### 采购风险雷达

风险雷达作为机会详情中的辅助区，而不是另建一个孤立页面。每个信号必须显示：计算依据、使用字段、阈值、原始样本、数据完整度和“需人工复核”提示。

## 五、为什么这比继续堆功能更有竞争力

- **业务结果明确**：评委看到的不是“搜到 20 条公告”，而是一项机会已经被拆成可执行任务。
- **多智能体真实可见**：不同 Agent 对同一份文件承担不同责任，并通过分歧和复核机制协作，不是把多个名字印在界面上。
- **飞书不是外挂**：每条文书要求都能落到成员、任务、截止日和回写状态。
- **证据链贯穿全程**：从公告原文到需求、判断、分工和决策都可追溯。
- **可以量化验收**：要求召回率、证据定位准确率、强制项漏检率、低置信度复核率、任务同步成功率都可以现场展示。

## 六、实施顺序与验收标准

### P0：投标要求账本与合规矩阵

范围：选择已捕捉公告及附件，生成带证据定位的结构化要求；支持人工编辑、确认和状态流转。

验收：准备 3 套公开招标文件人工标注集；强制项、截止时间、附件清单和评分项分别统计准确率/召回率；所有模型结论能定位到文件与页码或章节；未识别内容明确标记，不静默补全。

### P1：多智能体会审与人工复核

范围：在现有 TenderGraph 中加入结构、合规、技术、商务和证据审计节点；显示节点进度、输出、置信度、分歧和复核状态。

验收：节点可 checkpoint/resume；单节点失败不丢失前序结果；低置信度和冲突项稳定进入人工复核；人工确认后不会被后续 Agent 覆盖。

### P2：飞书投标战情室

范围：要求账本同步多维表格；按负责人创建任务；卡片动作双向回写；临期和强制项升级提醒。

验收：同一要求重复同步不产生重复任务；负责人使用真实 `open_id`；Web、SQLite、飞书三端状态一致；失败可重试且审计可查。

### P3：采购风险雷达

范围：先做投标窗口、采购人/供应商集中度、重大变更和价格异常四类可解释信号。

验收：每个指标有固定公式、测试样例和数据充分性判断；字段不足时显示“无法计算”；任何异常只表达为复核线索。

### P4：市场主题与竞争趋势

范围：离线生成品类趋势、采购人画像、供应商集中度和主题变化快照。

验收：小样本不输出伪精确趋势；名称归一化可人工修订；图表可从聚合值下钻到原始公告。

## 七、比赛前应避免的方向

- 不要继续增加数据源数量作为主卖点，16 个来源已经足够支撑展示。
- 不要先做自动生成整份投标书，幻觉风险高，而且会削弱证据可信这一优势。
- 不要一次性实现所有红旗指标，先做数据真的支持、现场能解释的 3 到 4 个。
- 不要把 Agent 数量当成能力指标，评委更容易被可见的分工、冲突、复核和结果回写说服。
- 不要照搬候选项目 UI 或文案；融合的是机制，并继续使用 TenderTrace 自己的产品语言和设计体系。

## 八、建议的路演一句话

> TenderTrace 不只帮团队找到招标，它会读懂招标文件，把每一项要求变成有原文依据、有人负责、有截止时间、能在飞书中闭环的投标准备任务。
