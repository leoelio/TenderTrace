## 一、执行摘要

方向十一已经从“同标题公告列表”升级为可解释、可复核、可人工裁决的跨来源关系图。系统可以把同一采购项目的原公告、更正公告、转载页面、附件和后续结果放到一条关系链中，并逐条说明为什么认为它们有关联。系统不会在字段冲突时替用户选择所谓“真值”，而是把冲突字段及双方原文入口送入事实复核区。

本次实现采用轻量集成方式：能力放在原有项目数字档案内，默认折叠，仅在需要解释来源时展开。它没有新增主导航，没有替换现有采集、评分、项目工作流或飞书功能。

独立验收结果：

- 真实主案例包含2个来源、2种公告类型、3个时间线节点。
- 2条跨来源关系均有明确匹配依据和置信度来源。
- 人工“确认合并”“拆分并锁定”“锁定合并”均已落库并写入审计记录。
- 人工拆分后重复执行增量构图，拆分决定仍然生效。
- 字段冲突不会自动裁决，测试案例可从冲突两侧直接回到原始网页。
- 已确认关系进入数字孪生时间线，并按公告去重。
- 已验证一组高相似但实为不同采购项目的误合并风险，系统已拆分并锁定。
- 真实机会索引总量升级前后均为45条，没有通过增加演示假数据制造通过结果。
- 专项测试12项通过，前端工作台脚本测试2项通过；全量回归517项测试、576项子测试全部通过，0项失败。

## 二、原问题与本次目标

同一个采购项目可能先后出现在采购人官网、公共资源平台、政府采购网和商业转载平台，并以采购公告、更正公告、答疑、结果公告、合同或附件等不同形态出现。只按标题搜索会产生两个风险：

1. 同一项目被当成多条互不相关的机会，造成重复跟踪、重复提醒和时间线断裂。
2. 不同项目因标题相似而被错误合并，导致金额、采购人、供应商或截止时间串线。

方向十一的目标不是追求“自动合并越多越好”，而是让每一条关系都可解释、可回源、可人工修正，并让人工决定在后续增量运行中保持有效。

## 三、产品落位与交互设计

### 3.1 接入现有项目数字档案

“来源可信关系”位于项目数字档案的“来源与证据可信度”之后。默认状态为折叠，并显示“按需展开 · 不占用主流程”。这样既保留原有档案阅读顺序，也避免评委或普通用户第一次进入项目时面对过多关系细节。

展开后依次看到：

- 已确认关系数、候选关系数、冲突字段数、已阻断误合并数。
- 当前公告和关联公告形成的节点与连线。
- 每条连线的匹配依据、分数和人工状态。
- 字段冲突复核区。
- 已阻断误合并记录。
- 去重后的项目时间线。
- 人工确认、拆分和锁定操作。

### 3.2 节点表达

节点按内容类型区分原公告、更正、答疑、结果、附件和其他公告；按来源性质区分：

- **官方来源：** 采购人官网或明确的官方采购平台。
- **转载来源：** 商业聚合或转载页面。
- **人工关系：** 经过人员确认并锁定的关系。

每个节点保留原始标题、发布时间、来源名称和原文链接。用户不需要相信关系图本身，可以直接打开原文核验。

### 3.3 边与匹配依据

每条关系边均显示匹配依据。当前依据包括：

- 项目编号完全一致。
- 标题相似度。
- 采购人一致。
- 地区一致。
- 预算或金额接近。
- 发布时间接近。

确定性规则与相似度依据分开输出。项目编号完全一致属于确定性证据；标题、地区、金额和时间属于候选证据。前端不会把两者包装成同一种“AI置信度”。

## 四、关系判断与防误合并机制

### 4.1 轻量本地计算

关系图直接读取本地 SQLite 公告、版本、附件和人工裁决记录，不触发外部网络采集。每次只围绕当前项目计算相关候选簇，适合现有本地环境和比赛现场。

### 4.2 确定性与相似性分层

关系判断先检查可验证的确定性字段，再评估相似字段。系统保存并返回每个依据，而不是只输出一个无法解释的总分。

典型判断顺序：

1. 项目编号一致时形成强关联候选。
2. 没有编号或编号无法比对时，综合标题、采购人、地区、金额和时间。
3. 出现关键字段冲突时，关系进入冲突复核，而不是自动选边。
4. 存在人工决定时，人工决定优先于自动候选。

### 4.3 冲突处理

冲突区同时展示A侧值、B侧值以及两侧原文链接。当前实现不把“来源等级高”直接等同于“字段一定正确”，也不自动覆盖另一侧数据。人员完成事实核验后，再决定合并、拆分或锁定。

### 4.4 人工操作与持久化

系统支持三类人工动作：

- **确认合并：** 确认当前两条记录属于同一项目，仍允许后续再次复核。
- **拆分并锁定：** 明确两条记录不是同一项目，后续增量构图不得再次自动合并。
- **锁定合并：** 确认属于同一项目，并阻止后续自动规则改变该结论。

每次操作要求填写操作者和原因，并记录操作前后状态。数据库采用规范化公告对作为唯一键，避免从A到B和从B到A形成两份互相矛盾的决定。

## 五、数据结构与接口

### 5.1 数据库

数据库模式升级到48，新增：

1. `notice_relation_decisions`：保存公告对、决定、锁定状态、操作者、原因和时间。
2. `notice_relation_audit_events`：保存动作、变更前状态、变更后状态和审计时间。

两张表均建立查询索引。既有公告、采集运行和项目工作流表未改变语义。

### 5.2 服务

新增轻量关系服务，负责：

- 构建当前项目的公告、版本和附件节点。
- 计算确定性依据和相似度依据。
- 识别冲突并保留两侧原始证据。
- 应用人工决定和锁定。
- 输出去重后的确认时间线。
- 统计已阻断的高相似误合并。

### 5.3 接口

- `GET /api/opportunities/{notice_id}/source-relations`：读取当前项目的可信关系图。
- `POST /api/opportunities/{notice_id}/source-relations/{related_notice_id}/decision`：提交确认、拆分或锁定决定。

决定接口返回更新后的关系图，页面无需刷新整个项目即可看到结果；随后数字孪生时间线同步刷新。

## 七、与数字孪生时间线的联动

已确认关系会进入原有项目数字孪生时间线，形成原公告、更正和转载等连续事件。时间线按公告ID去重，因此同一条转载或同一条已确认关系不会重复出现。

当前主案例：

- 数字孪生统计显示2条已确认来源关系。
- 时间线中出现2条关联公告事件。
- 关系图自身输出3个去重节点，覆盖当前公告和两条关联记录。

未确认候选和已拆分关系不会进入正式时间线，避免把猜测呈现为项目事实。

## 十一、通俗操作指南

### 11.1 查看一个项目的来源关系

1. 打开本地站点并进入“机会情报”。
2. 打开目标机会的项目数字档案。
3. 找到“来源可信关系”。
4. 点击展开，查看关系数量、公告节点和每条连线的匹配依据。
5. 对需要核验的记录点击“查看原文”。

### 11.2 确认两条记录属于同一项目

1. 比对项目编号、采购人、标题、金额和发布时间。
2. 填写操作者名称和判断原因。
3. 普通确认点击“确认合并”。
4. 已经充分核验且不希望自动规则改变时，点击“锁定合并”。

### 11.3 发现误合并

1. 打开双方原文，重点核对采购人、供应商、金额和项目编号。
2. 填写拆分原因。
3. 点击“拆分并锁定”。
4. 重新打开项目时，该关系仍会保持拆分。

### 11.4 发现字段冲突

不要直接选择看起来更权威的一侧。先在冲突区打开A、B两侧原文，核验发布时间和公告类型，再做合并或拆分决定。系统不会替用户自动覆盖字段。

## 十二、比赛展示脚本

建议用40至60秒展示方向十一：

1. 打开主案例数字档案，展开“来源可信关系”。
2. 指出同一项目包含官方原公告、官方更正和转载更正。
3. 点击一条边，说明系统展示项目编号、标题、采购人、地区和时间等依据。
4. 点击原文链接，证明每条关系可回源。
5. 展示“已阻断误合并1项”，说明系统会记住人工拆分。
6. 下滑到确认时间线，说明关系已进入数字孪生，而不是停留在孤立分析页。

推荐讲解句：

> 我们不仅知道网上有几条相似公告，还能解释它们为什么属于同一项目；如果系统猜错，人的一次拆分会被长期记住，不会在下一次刷新时重新犯错。

## 十三、风险边界与下一步

当前版本已经满足本方向的比赛验收目标，同时保留以下诚实边界：

1. 主案例覆盖原公告、更正和转载，结果公告、答疑和附件已在模型中支持，但当前真实主案例尚未同时覆盖全部类型。
2. 相似度规则用于提出候选，不代表法律或事实认定；关键冲突仍需人员核验原文。
3. 当前规模适合按项目簇即时计算。数据量显著增长后，可增加持久化候选缓存，但现阶段不需要引入图数据库。
4. 商业转载页面可能随登录策略或网站改版变化；本地已保存证据和官方来源仍是主要核验依据。
5. 自动截图工具连接故障应单独修复，但它不影响产品站点、关系接口或用户在浏览器中的实际操作。

建议的后续增强顺序：

1. 选择包含采购公告、答疑、更正、结果和合同的完整真实项目，扩充比赛主案例。
2. 在事实复核完成后，把经过确认的字段差异同步给公告变更影响引擎。
3. 增加人工裁决统计，展示系统提出候选后被确认和被拆分的比例。
4. 当数据规模达到数万级后，再评估候选索引和离线批量计算，不提前引入复杂图数据库。
