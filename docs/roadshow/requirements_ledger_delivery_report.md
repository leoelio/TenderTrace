## 2. 已实现能力

### 2.1 公告变化影响要求账本

公告的截止时间、预算、正文、附件、项目编号、采购人等字段发生变化后，系统会按变化类型定位可能受影响的要求：

- 截止时间变化只影响“截止时间”类要求。
- 预算变化影响“评分项”类要求。
- 正文、附件、项目编号、采购人等关键变化触发相关要求的全面证据复核。
- 受影响要求在页面上显示“待复核（原：已确认/待确认等）”。

这一展示状态不会覆盖 `opportunity_requirements` 中原有的人工状态。公告修订保存在 `notice_revisions`，重大变更复核与会审创建/裁决均写入 `opportunity_events`，因此能够追溯“为什么需要复核”和“谁做了裁决”。

主要接口：

- `GET /api/opportunities/{notice_id}/requirements`
- `POST /api/opportunities/{notice_id}/requirements`
- `POST /api/opportunities/{notice_id}/requirements/extract`

### 2.2 要求账本与规则提取

要求账本支持资格条件、截止时间、评分项、废标条款、附件清单五类要求。每项保留：原文摘录、原文定位、来源链接、强制性、置信度、负责人、截止日和人工状态。

规则提取可以从公告和已提取附件文本建立初始账本；已被人工确认的条目不会被后续规则提取静默覆盖。

### 2.3 飞书投标战情室编排

数字档案的“飞书协同”区域会读取：

- `GET /api/opportunities/{notice_id}/war-room`

该接口只返回本地计划，不访问飞书，也不创建外部资源。计划会显示以下四步的就绪状态及前置条件：

1. 复用已配置的飞书群并发送战情室卡片。
2. 根据机会负责人创建主责跟进任务。
3. 根据投标截止时间创建日历提醒。
4. 将机会工作流同步到飞书多维表格。

页面上的既有“启动飞书协同”操作仍调用 `POST /api/opportunities/send-feishu`。该操作才会通过已有集成创建卡片、主任务、日历事件，并同步团队和工作流台账。飞书凭据只从环境变量或 `.env.local` 读取，未写入源码、测试或本报告。

### 2.4 五角色会审工作流

会审板把以下情况生成可审计会审项：

- 要求本身标记为“待复核”。
- 置信度低于 70。
- 强制要求仍处于待处理状态。
- 公告版本变化已影响该要求。

系统根据要求类别和原文特征分派到合规、项目统筹、商务、文书、技术、证据审计角色。会审板支持：

- `GET /api/opportunities/{notice_id}/review-board`：读取已有会审项。
- `POST /api/opportunities/{notice_id}/review-board/sync`：按规则幂等生成缺失会审项。
- `POST /api/opportunities/{notice_id}/review-board/{review_id}/resolve`：记录采纳、退回修订或升级会审，以及裁决人和依据。

生成会审项与记录裁决均进入机会事件流；“裁决”不会直接改写要求的原状态、原文或人工结论。

## 4. 当前边界与未完成项

以下内容尚未完成，或需外部配置后再验证：

1. **真实飞书端到端验证**：尚未使用真实 App 凭据和真实群、任务、日历、多维表格进行现场验证；当前由本地契约与 Mock 飞书客户端覆盖接口行为。
2. **自动创建新飞书群**：战情室当前复用已配置群，不主动创建群聊。
3. **要求级飞书同步**：尚未把每条要求写入多维表格、为每条要求创建 Task v2，也尚未实现状态双向回写和幂等同步。
4. **真实多 Agent 会审**：当前会审是规则路由和人工裁决工作流；尚未接入多个模型/Agent 的独立意见、分歧比较和自动会审建议。
5. **真实浏览器交互回归**：静态 JS 语法与 API/契约测试已通过，但尚未进行带真实浏览器和真实飞书配置的完整演示回归。
