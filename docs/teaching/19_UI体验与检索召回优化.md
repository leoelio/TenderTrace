# 19 UI 体验与检索召回优化

## 你要理解的核心问题

这次不是单纯“美化界面”。真正的问题有三层：

1. 用户输入“杭州市”时，旧解析器只认识省份，所以把“杭州市”当成主题词。
2. GGZY 对 36 个月这样的长时间窗会报“开始时间错误”。
3. 城市字段在不同来源中并不稳定，如果强制城市精确匹配，容易漏召回。

所以代码必须先修底层逻辑，再改 UI。

## 代码片段 1：城市解析

文件：`tendertrace/intent/region.py`

```python
_CITIES: dict[str, tuple[str, str, tuple[str, ...]]] = {
    "杭州": ("浙江", "330100", ("杭州", "杭州市")),
}
```

这段代码的含义：

- key 是标准城市名。
- 第一个值是所属省份。
- 第二个值是城市 adcode。
- 第三个值是用户可能输入的别名。

解析结果里仍然保留 `adcode=330000`，因为 GGZY 的省份筛选使用省级编码；同时新增 `city_adcode=330100` 作为城市语义证据。

## 代码片段 2：多主题解析

文件：`tendertrace/intent/topic.py`

```python
text = re.sub(r"(或者|或是|以及|和|与|及|或)", " ", text)
core = tokens[:3] or []
```

这让：

```text
空调或者服务器
```

变成：

```json
["空调", "服务器"]
```

后续匹配逻辑是 OR，不是 AND。也就是说标题或正文命中任一主题即可。

## 代码片段 3：开放主题

文件：`tendertrace/intent/topic.py`

```python
"open_scope": not core and ("全部" in query or "不限主题" in query)
```

如果用户说“全部投标信息”，主题可以为空。否则主题为空会进入 `clarify_needed`。

这避免了两个错误：

- 把“全部”当关键词。
- 要求用户补充主题，但用户其实已经明确要全量。

## 代码片段 4：长时间窗降级

文件：`tendertrace/adapters/ggzy.py`

```python
if isinstance(window, dict) and window.get("from") and window.get("to") and _site_accepts_window(window):
    body["TIMEBEGIN"] = str(window["from"])
    body["TIMEEND"] = str(window["to"])
else:
    body["DEAL_TIME"] = "02"
```

GGZY 对超长时间范围不接受。直接传 36 个月会失败。

这里的策略是：

1. 站点能接受短时间窗时，传精确日期。
2. 站点不能接受长时间窗时，使用站点支持的相对时间参数。
3. 抓回来以后仍然用本地 BidQL 过滤，不把站点结果直接当最终答案。

## 代码片段 5：城市降级

文件：`tendertrace/adapters/multi.py`

```python
if not notices and _has_city_scope(bidql):
    notices = adapter.collect(
        _without_city_scope(bidql),
        max_pages=max_pages,
        max_results=max_results,
    )
    relaxed_city = bool(notices)
```

这段代码解决的是“城市字段不稳定”。

策略是：

1. 先严格按杭州查。
2. 如果某个来源 0 条，再放宽到浙江省。
3. 如果放宽后有结果，记录 `relaxed_city=true`。

注意：这里没有放宽主题。搜索“空调或者服务器”时，仍然必须命中空调或服务器。

## 代码片段 6：模型策略

文件：`tendertrace/runner.py`

```python
if strategy == "rules":
    return replace(settings, model_enhancement_enabled=False)
if strategy == "local":
    return replace(settings, model_mode=ModelMode.LOCAL, model_enhancement_enabled=True)
if strategy in {"cloud", "hybrid"}:
    return replace(settings, model_mode=ModelMode.CLOUD, model_enhancement_enabled=True)
```

这让每次运行可以独立选择模型策略，而不是只能依赖 `.env.local`。

UI 中的含义：

- 跟随配置：使用当前 `.env.local`
- 本地规则：不调用模型
- 本地模型：调用 Ollama
- 云端模型：调用 OpenAI
- 规则+云端：规则解析后再做云端增强

## 代码片段 7：订阅计划覆盖

文件：`tendertrace/scheduling/subscriptions.py`

```python
schedule_override={"kind": "recurring", "frequency": "daily", "time": "09:00"}
```

旧逻辑要求用户在问题里写“每天9:00发送给我”。

新逻辑允许 UI 直接传计划对象。这样订阅设置更清晰，也更适合普通用户。

## 前端结构

文件：`web/dist/index.html`

核心结构：

- `chat-panel`：对话和输入。
- `run-panel`：运行概览。
- `trace-panel`：事件流。
- `sources-panel`：来源和模型。
- `subscription-panel`：订阅。
- `outbox-panel`：Word 文件。

前端没有硬编码结果。它只调用 API：

```javascript
POST /api/runs
POST /api/subscriptions
GET /api/traces/{run_id}
GET /api/outbox
```

## 调试思路

当你看到 0 条结果时，不要先怀疑 UI。按这个顺序查：

1. `parse-intent`：区域、主题、时间有没有解析错。
2. `runlog stats`：source_stats 有没有站点错误。
3. `raw_count`：有没有原始候选。
4. `duplicates_removed`：是不是去重合并了。
5. `relaxed_city`：有没有发生城市降级。
6. `notice_count`：最终写入 Word 的条数。

## 本阶段验证

真实命令：

```powershell
python -m tendertrace run-once "最近36个月杭州市的空调或者服务器投标信息都有哪些" --max-pages 5 --max-results 8 --model-strategy rules
```

结果：

```text
notice_count: 3
raw_count: 6
duplicates_removed: 3
source_sites: ggzy
relaxed_city: true
```

这证明系统没有硬编码结果，而是通过真实来源、扩展检索、城市降级、清洗去重得到结果。
