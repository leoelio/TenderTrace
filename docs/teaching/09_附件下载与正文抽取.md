# 09 附件下载与正文抽取

## 本阶段解决什么问题

招投标公告经常把最关键的信息放在附件里，例如采购需求、技术参数、评分办法、清单、合同模板。P8 已经能在报告里保留附件链接，但还没有读取附件正文。

P9 的目标是把附件从“链接”升级为“可审计证据”：

- 下载附件。
- 缓存在本地快照目录。
- 计算文件哈希。
- 从 PDF、DOCX、XLSX 抽取正文。
- 把附件正文合入证据链。
- 把附件处理状态写入数据库和 Word。

这样报告不只告诉用户“有附件”，还能告诉用户“附件里有什么可用证据”。

## 源码地图

- `tendertrace/pipeline/attachments.py`：附件下载与正文抽取。
- `tendertrace/pipeline/evidence.py`：把附件正文纳入事实校验。
- `tendertrace/runner.py`：在状态图中接入附件处理。
- `tendertrace/db.py`：新增附件账本表。
- `tendertrace/report/docx_writer.py`：报告展示附件解析结果。
- `web/dist/app.js`：Web 展示附件正文抽取数量。
- `tests/test_pipeline_attachments.py`：PDF/DOCX/XLSX 抽取测试。

## 为什么附件处理要独立成模块

适配器负责从网页中提取附件链接。附件下载和正文抽取不应该写进适配器，原因有三个：

1. 多个来源站点都需要同一套附件处理逻辑。
2. 下载和解析有独立的安全阈值、缓存和错误处理。
3. 后续接 OCR、更多文件格式时，不应该修改每个采集适配器。

所以 P9 新增：

```python
tendertrace/pipeline/attachments.py
```

它的输入是 `Notice`，输出仍然是 `Notice`，只是在 `fields` 中增加 `attachment_snapshots`。

## AttachmentSnapshotResult

附件模块的返回对象是：

```python
@dataclass(frozen=True)
class AttachmentSnapshotResult:
    notices: list[Notice]
    stats: dict[str, object]
```

`notices` 是带附件快照字段的公告列表。

`stats` 是运行统计，例如：

- `attachments_seen`
- `attachments_attempted`
- `attachments_downloaded`
- `attachments_extracted`
- `attachments_skipped`
- `attachments_failed`

这些统计会进入 `runs.stats_json`，也会在 trace 中显示。

## enrich_attachment_snapshots 主流程

核心入口：

```python
def enrich_attachment_snapshots(
    notices: list[Notice],
    *,
    settings: Settings,
    max_per_notice: int,
    max_bytes: int,
    downloader: Downloader | None = None,
) -> AttachmentSnapshotResult:
```

这里有一个测试友好的设计：`downloader` 可以注入。

正常运行不传 `downloader`，系统使用真实 HTTP 下载。

测试时传 fake downloader，就可以用内存里的 PDF/DOCX/XLSX 字节验证解析逻辑，不依赖外网。

## 下载安全阈值

P9 新增配置：

```env
TENDERTRACE_ATTACHMENT_MAX_PER_NOTICE=3
TENDERTRACE_ATTACHMENT_MAX_BYTES=8388608
```

对应 `Settings` 字段：

```python
attachment_max_per_notice: int
attachment_max_bytes: int
```

为什么必须有阈值？

真实招投标附件可能很大。没有阈值时，一次任务可能因为一个几十 MB 的附件变慢甚至失败。P9 的策略是：超过限制就记录为 `skipped`，而不是让整次运行失败。

## 下载函数如何限制大小

默认下载函数使用流式读取：

```python
with client.stream("GET", url) as response:
    response.raise_for_status()
    for chunk in response.iter_bytes():
        total += len(chunk)
        if total > max_bytes:
            raise ValueError(f"attachment exceeds {max_bytes} bytes")
        chunks.append(chunk)
```

这样可以边下载边计数，不需要等完整文件下载完才发现超限。

## 缓存路径如何生成

附件下载后会计算 SHA256：

```python
sha256 = hashlib.sha256(data).hexdigest()
```

然后写入：

```text
snapshots/attachments/<sha256前两位>/<sha256>.<type>
```

例如：

```text
snapshots/attachments/ab/ab12...ef.pdf
```

这种目录结构有两个好处：

1. 文件名稳定。
2. 大量附件不会全部堆在一个目录下。

## 支持哪些文件正文抽取

P9 支持三类：

```python
EXTRACTABLE_TYPES = {"pdf", "docx", "xlsx"}
```

PDF：

```python
reader = PdfReader(BytesIO(data))
for page in reader.pages[:8]:
    parts.append(page.extract_text() or "")
```

DOCX：

```python
document = Document(BytesIO(data))
parts = [paragraph.text for paragraph in document.paragraphs]
```

XLSX：

```python
workbook = load_workbook(BytesIO(data), read_only=True, data_only=True)
for sheet in workbook.worksheets[:3]:
    for row in sheet.iter_rows(max_row=50, max_col=12, values_only=True):
```

这里都做了页数、表格、行列限制，防止附件解析无限膨胀。

## 为什么暂不处理扫描版 PDF

`pypdf` 只能抽取 PDF 内已有文本层。扫描版 PDF 本质上是图片，需要 OCR。

P9 不引入 OCR，原因是 OCR 需要额外模型或系统依赖，验证成本更高。当前阶段先把文本层 PDF、DOCX、XLSX 跑通，后续再做 OCR 更稳。

## attachment_snapshots 字段长什么样

每个附件会生成一条记录：

```python
{
    "name": name,
    "url": url,
    "canonical_url": canonicalize_url(url),
    "type": kind,
    "status": status,
    "path": str(path),
    "sha256": sha256,
    "bytes": len(data),
    "text_excerpt": text[:1200],
    "text_length": len(text),
    "error": "",
}
```

`status` 常见值：

- `extracted`：已下载并抽取到正文。
- `downloaded`：已下载，但没有可抽取正文。
- `skipped`：因为未知类型或超过数量限制跳过。
- `failed`：下载或解析失败。

P9 只下载可抽取正文的 PDF、DOCX、XLSX。ZIP、RAR、DOC、XLS 等格式会保留链接并记录为 `skipped`，避免为了无法抽取正文的文件消耗下载时间。

## evidence 如何使用附件正文

P8 的证据文本只来自公告标题、正文和核心内容。

P9 后，`_evidence_text()` 会把附件正文片段也加进去：

```python
attachment_text = " ".join(
    str(record.get("text_excerpt") or "")
    for record in _attachment_records(notice)
)
```

这样如果核心内容来自附件，而不是公告正文，事实校验也能找到依据。

## runner 中的接入顺序

P9 后，`runner.evidence()` 的顺序是：

```python
attachment_result = enrich_attachment_snapshots(...)
notices = attachment_result.notices
context.emit_tool_call("pipeline.attachment_extract", attachment_result.stats)

evidence_result = attach_evidence(notices)
notices = evidence_result.notices
_persist_notices_and_clusters(settings, notices)
```

先附件，后证据。

原因是：附件正文是证据的一部分。

## attachment_snapshots 表

数据库新增：

```sql
CREATE TABLE IF NOT EXISTS attachment_snapshots (
    id TEXT PRIMARY KEY,
    notice_id TEXT NOT NULL,
    cluster_key TEXT NOT NULL,
    name TEXT NOT NULL,
    url TEXT NOT NULL,
    type TEXT,
    status TEXT NOT NULL,
    local_path TEXT,
    sha256 TEXT,
    bytes INTEGER NOT NULL DEFAULT 0,
    text_excerpt TEXT,
    text_length INTEGER NOT NULL DEFAULT 0,
    error TEXT
)
```

这张表是文件级账本。它回答的是：

- 哪个公告有哪个附件？
- 这个附件有没有下载成功？
- 文件哈希是什么？
- 是否抽取到正文？
- 失败原因是什么？

## 测试如何证明 P9 生效

附件模块测试用内存生成文件：

```python
files = {
    "https://example.com/spec.pdf": _pdf_bytes("project SH-2026-001 budget 120"),
    "https://example.com/spec.docx": _docx_bytes("docx project requirement server"),
    "https://example.com/spec.xlsx": _xlsx_bytes("xlsx equipment list"),
}
```

然后 fake downloader 返回这些字节：

```python
def fake_download(url: str, max_bytes: int) -> bytes:
    return files[url]
```

这样测试覆盖了解析能力，但不会访问互联网。

runner 测试进一步验证：

- `attachment_snapshots` 入库。
- `attachments_extracted` 写入 run stats。
- Word 中出现 `附件解析` 和 `附件正文摘录`。

## 本阶段你需要掌握的关键概念

1. 附件不是附属信息，在招投标场景里经常是核心证据。
2. 下载必须有大小和数量限制，否则系统稳定性不可控。
3. 文件哈希是附件版本追踪的关键。
4. PDF 文本层抽取和 OCR 是两回事。
5. 附件正文应该进入证据链，而不是只进入报告。
6. 下载失败不能中断报告生成，应记录为可追踪状态。
