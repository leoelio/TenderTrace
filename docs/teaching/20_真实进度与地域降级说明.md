# 20 真实进度与地域降级说明

## 学习目标

这一节讲解两个工程判断：

1. 为什么“真实进度”需要后端先返回 `run_id`，再由前端轮询 checkpoint。
2. 为什么“杭州无结果后扩大到浙江省内”必须成为结构化数据，而不是只在 UI 里写一段提示。

## 一、同步接口为什么不适合做真实进度

原来的 `/api/runs` 会等 `run_once` 完整执行结束后才返回。前端在这段时间拿不到 `run_id`，也就无法查询：

- trace events
- checkpoints
- run stats

因此前端只能用定时器伪造进度。这会造成用户看到所有步骤都像在运行，却不知道真实执行到哪里。

P20 新增：

```python
@app.post("/api/runs/start")
def start_run_api(request: dict[str, object] = Body(...)) -> dict[str, object]:
    run_id = str(uuid4())
    thread = Thread(
        target=run_once,
        kwargs={..., "run_id": run_id},
        daemon=True,
    )
    thread.start()
    return {"run_id": run_id, "status": "queued"}
```

这段代码的关键不是“线程”，而是“先确定 run_id”。只要 run_id 稳定，前端就可以轮询后端真实状态。

## 二、前端如何显示真实进度

前端提交任务后调用：

```javascript
const start = await api("/api/runs/start", {
  method: "POST",
  body: JSON.stringify(payload),
});
```

然后进入轮询：

```javascript
const result = await pollRunUntilFinished(start.run_id);
```

`pollRunUntilFinished` 每轮读取三类数据：

- `/api/traces/{run_id}`：工具调用事件。
- `/api/checkpoints/{run_id}`：状态图节点完成情况。
- `/api/runs/{run_id}`：最终统计、错误、报告路径。

进度卡的阶段状态来自 checkpoint：

```javascript
const nodes = new Set(checkpoints.map((checkpoint) => checkpoint.node));
```

如果 `intent` 已经完成，意图解析显示“已完成”；如果 `collect` 未完成，数据采集显示“进行中”或“等待”。这比定时器更可靠，因为它反映的是后端已经写入数据库的状态。

## 三、地域降级为什么不能只在前端写死

用户问的是“杭州市”。如果结果直接显示浙江省，会造成语义错位：

- 用户以为系统找到了杭州记录。
- 实际上系统可能是在杭州无样本后扩大到浙江省内。
- 这属于检索范围变化，必须透明披露。

因此后端生成结构化字段：

```python
{
    "status": "relaxed_city",
    "requested_city": city,
    "requested_province": province,
    "fallback_region": province,
    "relaxed_sources": relaxed_sources,
    "message": message,
}
```

这个字段写入 run stats，也写入 BidQL meta。

这样 UI 和 Word 报告都不需要猜测，只要读取同一个字段。

## 四、Word 报告如何保持可信

报告生成器读取 `bidql["meta"]["region_scope"]`：

```python
if scope.get("status") == "relaxed_city" and city and province:
    return f"{city}（城市级无结果，已扩大至{province}省内）"
```

这让报告头部直接说明真实范围：

```text
地区：杭州（城市级无结果，已扩大至浙江省内）
地域范围说明：杭州城市级检索未命中样本，已扩大到浙江省内检索；结果可能包含省内周边城市，请以来源链接为准。
```

这个设计避免了“报告与 UI 说法不一致”的问题。

## 五、如何验证

运行：

```powershell
python -m unittest discover -s tests -v
python -m tendertrace acceptance-check
```

再打开 Web：

```powershell
python -m tendertrace serve
```

输入：

```text
最近36个月杭州市的空调或者服务器投标信息都有哪些
```

观察：

- 运行中只有当前阶段是“进行中”。
- 来源明细中出现“城市无结果后省内扩展”。
- 最终回复出现杭州到浙江省内的范围说明。
- 下载 Word 后，报告头部也有同样说明。

## 六、扩展思考

真实系统里，检索降级要遵守一个原则：可以扩大召回，但必须披露范围变化。

类似规则还可以扩展到：

- 主题降级：精确关键词无结果后扩展同义词。
- 时间降级：指定日期无结果后扩展到最近一个月。
- 来源降级：登录源失败后仅使用公开源。

每一种降级都应该写入结构化 stats，而不是只写 UI 文案。
