# 23 金标召回评测与向量增强

本节解释 P23 的关键设计。它的目标不是让评测页更好看，而是让“召回率提升”这句话可以被验证。

## 一、为什么不能自动生成金标

如果系统先抓到一批结果，再把这些结果写成金标，那么评测会变成自证循环：

```text
系统召回了 A -> 金标里有 A -> 系统召回正确
```

这没有证明召回能力，只证明系统能再次找到自己曾经找到过的东西。

所以 `docs/evaluation/gold_benchmark.json` 只放 10 个查询，不自动填 `gold_notices`。人工必须打开源站链接，确认某条公告确实应该被这个查询召回，再把它写入金标。

## 二、Recall@K 的计算方式

`tendertrace/gold.py` 会读取金标，然后对每个已标注 case 执行本地检索：

```python
retrieved = search_notices(settings, bidql, max_results=max_k).notices
```

金标和召回结果通过三类键匹配：

- `source_site + notice_id`
- 规范化后的 `source_url`
- 规范化后的标题

注意：一条金标公告可以有多个匹配键，但分母按公告条数计算，不按键数量计算。

## 三、为什么保留 recall_proxy

真实 Recall@K 依赖人工金标。金标没有标注之前，严格召回率不能声称可用。此时面板继续展示 `recall_proxy`，它仍然能反映来源覆盖、FTS 覆盖、本地复用和去重保留趋势。

有金标后，总分中的召回项会优先使用 `strict_recall_at_10`。

## 四、采集订阅和用户订阅的边界

用户订阅的目标是“按时间生成 Word 并推送新增内容”，所以它必须写 `sent_history`。

采集订阅的目标是“持续养大本地 notices 库”，所以它不生成 Word，也不写 `sent_history`。这两个概念分开后，后台采集不会污染用户推送账本。

## 五、向量检索为什么默认关闭

向量检索需要本地模型依赖和向量构建时间。当前库规模还小时，FTS5 已经有明显收益；向量更适合库变大、同义表达更多的时候。

因此系统只提供可选增强：

1. 安装 `.[vector]`。
2. 设置 `TENDERTRACE_VECTOR_ENABLED=true`。
3. 执行 `python -m tendertrace embed-notices`。
4. 查询时执行 FTS + vector 双路召回，最后用 RRF 融合。

这比默认强行启用更稳，也符合工业系统逐步增强的方式。

## 六、关键代码地图

| 文件 | 作用 |
|---|---|
| `tendertrace/gold.py` | 金标加载、候选导出、Recall@K 计算 |
| `docs/evaluation/gold_benchmark.json` | 10 个典型查询和人工金标入口 |
| `tendertrace/scheduling/ingest_subscriptions.py` | 独立采集订阅 |
| `tendertrace/vector.py` | 可选本地向量生成与覆盖率统计 |
| `tendertrace/retrieval.py` | FTS + vector 双路召回和 RRF 融合 |
| `tendertrace/evaluation.py` | Agent 评测页合并真实 Recall 与代理指标 |

## 七、验证点

- `tests/test_gold.py` 证明金标召回按人工标注公告计算。
- `tests/test_ingest_subscriptions.py` 证明采集订阅不写入用户订阅表。
- `tests/test_vector.py` 证明向量默认关闭，不影响离线运行。
- `tests/test_scheduler.py` 证明采集订阅 job 与用户订阅 job 分离。
