# 17 登录源状态校验与千里马验收

本节讲 P17 的核心：为什么“文件存在”不等于“登录态可用”，以及如何用最少代码把登录站点状态变成可解释、可测试、可录屏的证据。

## 1. 问题在哪里

早期实现里，`QianlimaSessionVault.has_storage_state()` 只判断：

```python
return self.storage_state_path.exists() and self.storage_state_path.stat().st_size > 0
```

这在工程上不够严谨。一个非空文件可能是：

- 空 JSON；
- 坏 JSON；
- 不是 Playwright `storage_state` 结构；
- 只包含其它网站的 Cookie；
- 已经过期或不可用的登录态。

所以 P17 把判断拆成结构化状态：`missing`、`empty`、`invalid_json`、`invalid_shape`、`empty_state`、`domain_missing`、`ready`。

## 2. 为什么只校验结构，不打印 Cookie

登录态文件里可能包含真实 Cookie。Cookie 本质上就是临时凭据，泄露后可能被复用。因此状态输出只能包含：

- 文件路径；
- 文件大小；
- 修改时间；
- Cookie 和 origin 的数量；
- 是否包含 `qianlima.com` 域名；
- 当前校验结论。

不能输出 Cookie 名称和值。测试里也专门断言 `status.to_dict()` 不包含模拟 Cookie 值。

## 3. ready 的含义

`ready` 不是“保证一定能抓到内容”。它表示本地 `storage_state` 至少满足三个条件：

1. 文件存在且可读。
2. JSON 结构符合 Playwright 的 `storage_state`。
3. 存在千里马域名相关 Cookie 或 origin。

真正访问网站的结果还可能受网络、验证码、会员权限、站点改版影响，所以系统另外提供：

```powershell
python -m tendertrace verify-qianlima --live
```

live 校验是提交前人工确认工具，不应该成为普通单元测试的一部分。

## 4. 代码阅读：状态对象

`QianlimaSessionStatus` 增加了几个字段：

```python
validation: str = "missing"
detail: str = "storage_state file is missing"
cookie_count: int = 0
origin_count: int = 0
qianlima_cookie_count: int = 0
qianlima_origin_count: int = 0
```

其中 `ready` 是一个派生属性：

```python
@property
def ready(self) -> bool:
    return self.validation == "ready"
```

这样 API、CLI、验收和 UI 不需要重复理解所有状态，只要看 `ready` 就能决定是否启用登录源。

## 5. 代码阅读：结构校验

`_validate_storage_state()` 先读取文件，再逐步检查：

```python
payload = json.loads(raw)
if not isinstance(payload, dict):
    return _validation("invalid_shape", "storage_state root must be a JSON object")
cookies = payload.get("cookies")
origins = payload.get("origins")
if not isinstance(cookies, list) or not isinstance(origins, list):
    return _validation("invalid_shape", "storage_state must contain cookies and origins lists")
```

这里没有为了“灵活”接受各种奇怪格式。原因是 Playwright 已经定义了稳定格式，接受非标准格式反而会让故障延后到采集阶段。

## 6. 代码阅读：CLI 入口

`verify-qianlima` 默认只做离线校验：

```powershell
python -m tendertrace verify-qianlima
```

如果返回码非 0，说明登录态还不能用于采集。加 `--live` 时，系统才会启动 Playwright：

```powershell
python -m tendertrace verify-qianlima --live
```

这种设计把“本地文件是否合理”和“外部网站当前是否可访问”分开，测试也更稳定。

## 7. Web UI 为什么也要显示 validation

赛题要求可运行系统和 Demo 演示。录屏时只展示“需要登录”不够，评委无法判断系统是否真的有登录源设计。

P17 后，来源面板会显示：

- `validation: missing` 或 `ready`；
- `cookies/origins` 计数；
- 具体 `detail`。

这能证明系统不是硬编码跳过登录源，而是有明确的登录态验证入口。

## 8. 测试思路

新增测试覆盖三类状态：

1. 没有文件：`missing`。
2. 空 Playwright 状态：`empty_state`，不能算 ready。
3. 千里马域名 Cookie：`ready`。
4. 非千里马域名 Cookie：`domain_missing`。

测试还确认 Cookie 值不会出现在 `to_dict()` 输出里。这是安全要求，不只是格式要求。

## 9. 工程取舍

本阶段没有尝试绕过验证码，也没有在代码里保存账号密码。这是正确边界。工业落地里，登录站点通常要遵守三个原则：

- 人工登录或官方授权；
- 本地保存短期会话；
- 会话失效时明确提示重新登录。

P17 做的是让这个过程可验证，而不是假装登录站点永远稳定。
