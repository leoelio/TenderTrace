# 14 本地模型自检与云端隔离

这一节解释 P14 为什么要加 `model-doctor`，以及它和 `model-status` 的区别。

## 为什么 P14 必要

项目同时支持本地模型和云端模型。用户很容易担心：

> 我已经配置云端 OpenAI 了，如果没有本地 Ollama，会不会影响运行？

答案取决于 `TENDERTRACE_MODEL_MODE`：

- `cloud`：只用 OpenAI 兼容 API，不需要 Ollama。
- `local`：使用 Ollama，需要本地服务和模型可用。
- `disabled`：完全不使用模型增强，规则解析、采集、报告仍可运行。

P14 的价值是把这个判断变成可执行证据，而不是口头解释。

## model-status 和 model-doctor 的区别

`model-status` 是状态快照：

```powershell
python -m tendertrace model-status
```

它只告诉你：

- 当前模式是什么。
- provider 是谁。
- 模型名是什么。
- 是否已配置。
- 模型增强是否启用。

`model-doctor` 是配置诊断：

```powershell
python -m tendertrace model-doctor
```

它会额外说明：

- cloud 模式下 Ollama 是否必要。
- local 模式下什么时候需要 Ollama。
- 模型增强关闭时主流程如何降级。

## 为什么默认不 live

live 探测会真的调用模型：

```powershell
python -m tendertrace model-doctor --live
```

如果当前是 cloud 模式，它会消耗一次云端请求。如果当前是 local 模式，它要求 Ollama 服务在线。因此默认 `model-doctor` 不联网，只做配置判断。

这和系统主流程一致：没有明确要求 live，就不额外制造外部依赖。

## 核心代码结构

P14 新增 `tendertrace/llm/doctor.py`：

```python
def model_doctor(settings, *, live=False, gateway=None):
    status = model_status(settings)
    checks = [
        provider_check(status),
        mode_dependency_check(settings),
        enhancement_check(settings),
    ]
    if live:
        checks.append(live_probe(gateway or ModelGateway(settings)))
```

这个结构有两个设计点：

1. 先做纯配置判断。
2. 只有 `live=True` 时才调用模型网关。

## 脱敏为什么放在网关层

模型 live 探测失败时，错误可能来自 HTTP 客户端、provider 或网络层。错误字符串里理论上可能夹带 `Bearer ...` 或 `sk-...`。

因此脱敏逻辑放在 `ModelGateway.generate_json()` 的异常路径里。这样无论是正常增强还是 doctor 探测，都复用同一套安全边界。

## Web 面板为什么只做非 live 自检

Web 工作台打开时会自动加载 Model 面板。如果默认 live 探测，就可能在用户不知道的情况下调用云端接口，或因为本地 Ollama 没开而弹错误。

所以 Web 只调用：

```text
GET /api/model/doctor
```

它是非 live 的配置自检。真正的 live 探测留给 CLI：

```powershell
python -m tendertrace model-doctor --live
```

## 本阶段验收点

1. cloud 模式下没有 Ollama 不影响运行。
2. local 模式可通过 `--live` 验证 Ollama `/api/chat`。
3. API 和 UI 都能展示自检结果。
4. 测试覆盖成功、失败和脱敏路径。
5. 文档明确说明 live 探测的调用成本和依赖。
