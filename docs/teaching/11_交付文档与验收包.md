# 11 交付文档与验收包

## 本阶段解决什么问题

代码能跑只是项目完成的一部分。赛题明确要求交付四类成果：

- 工具执行后的 Word 文件。
- 设计文档。
- 代码文件和操作文档。
- Demo 演示视频。

P11 的目标是把“能运行的系统”整理成“能交付、能复现、能验收的项目包”。

## 源码地图

- `docs/design/详设文档.md`：系统设计、模块职责、创新点。
- `docs/operation/操作文档.md`：安装、配置、运行、验证步骤。
- `docs/demo/Demo演示脚本.md`：录屏流程和讲解顺序。
- `docs/operation/P11_交付文档与验收包.md`：本阶段操作记录。
- `tests/test_delivery_docs.py`：交付文档存在性和敏感信息检查。
- `README.md`：项目入口说明更新。

## 为什么要单独做交付文档

阶段文档是开发过程记录，评委或新用户需要的是一份从零开始可复现的操作指南。P11 把分散信息收敛为三份顶层文档：

1. 设计文档回答“系统怎么设计、创新点在哪里”。
2. 操作文档回答“如何安装、运行、验证”。
3. Demo 脚本回答“如何录制并展示完整工作流”。

## 详设文档写什么

`详设文档.md` 覆盖：

- 项目定位。
- 需求覆盖。
- 总体架构。
- 核心模块设计。
- 数据库设计。
- 创新点。
- 安全与合规边界。
- 可验证性。
- 当前限制。

这对应赛题中的“需覆盖系统核心模块设计、功能实现创新点”。

## 操作文档写什么

`操作文档.md` 覆盖：

- 环境要求。
- 安装命令。
- `.env.local` 配置。
- 本地模型、云端模型、禁用模型三种模式。
- 初始化数据库。
- 启动 Web。
- 立即运行。
- 创建订阅。
- 登录千里马。
- 按赛题示例验证。
- Trace 验证。
- 回归测试。
- 常见问题。

这样一个新环境可以按文档复现，而不是依赖开发者口头解释。

## Demo 脚本写什么

Demo 脚本不是视频本身，但它规定录屏要覆盖：

- 系统状态。
- 立即执行问题。
- 第二个问题。
- 创建订阅。
- 登录态来源说明。
- 反硬编码证据。

录屏时按脚本走，就能覆盖赛题要求的“输入 -> 输出完整工作流”和“多个问题”。

## 为什么要写 test_delivery_docs

交付文档很容易后续被改名、漏删或误写敏感内容。测试能把这些要求固化：

```python
required = [
    Path("docs/design/详设文档.md"),
    Path("docs/operation/操作文档.md"),
    Path("docs/demo/Demo演示脚本.md"),
]
```

还会扫描文档和 README，防止出现类似真实 OpenAI key 的模式。

## 敏感信息检查边界

文档可以出现变量名：

```text
OPENAI_API_KEY
```

但不能出现真实 key。测试检查的是：

```python
re.compile(r"sk-(?:proj-)?[A-Za-z0-9_-]{20,}")
```

这可以防止把真实 key 粘进文档。

## README 为什么要更新

README 是项目入口。P10 完成后 README 仍写着 P9 和 55 tests，会误导验收人员。因此 P11 更新：

- 当前阶段改为 P11。
- 当前能力加入云端/本地模型增强。
- 测试基线改为 65 tests。
- 增加交付文档入口。

## 本阶段你需要掌握的关键概念

1. 工程交付不是只有代码，还包括可复现路径。
2. 阶段文档和最终操作文档服务对象不同。
3. Demo 脚本能减少录屏遗漏。
4. 交付文档也需要测试，尤其是存在性和敏感信息检查。
5. `.env.local` 可以存在于本机，但不能进入代码仓库或演示画面。
