# 07 清洗去重与聚类账本

## 本阶段解决什么问题

P6 之后系统已经能从两个公开源抓取公告。多源带来的下一个问题是重复：同一项目可能被政府采购网、公共资源交易平台、商业站点同步转载。如果不做清洗与聚类，报告会重复展示，订阅增量也可能重复推送。

P7 的目标是把候选公告变成可比较、可入账、可去重的公告：

- 清洗正文噪声。
- 规范化 URL。
- 提取项目编号。
- 计算 SimHash。
- 生成稳定 `cluster_key`。
- 合并跨源重复公告。
- 写入 `notices` 与 `clusters` 表。

## 源码地图

- `tendertrace/pipeline/dedup.py`：P7 的核心算法模块。
- `tendertrace/runner.py`：在 collect 节点接入清洗去重，并持久化 notice/cluster。
- `tendertrace/report/docx_writer.py`：报告展示关联来源。
- `tests/test_pipeline_dedup.py`：验证清洗、URL 规范化、SimHash、项目编号和跨源合并。
- `tests/test_runner.py`：验证 runner 统计和数据库账本。

## 为什么不能把去重写在适配器里

适配器只知道自己的网站。CCGP 适配器不知道 GGZY 返回了什么，GGZY 也不知道千里马返回了什么。如果把去重写进每个适配器，就只能做站内去重，无法做跨源聚类。

因此 P7 新增统一层：

```text
adapter.collect -> clean_and_cluster_notices -> sent_history incremental -> report
```

这样所有来源先统一成 `Notice`，再进入同一套清洗去重逻辑。

## URL 规范化

同一详情页可能因为统计参数不同而变成多个 URL：

```text
https://example.com/detail?a=1&utm_source=x#top
https://example.com/detail?a=1
```

`canonicalize_url()` 会去掉追踪参数和 fragment：

```python
def canonicalize_url(value: str) -> str:
    parsed = urlsplit(value.strip())
    scheme = (parsed.scheme or "https").lower()
    netloc = parsed.netloc.lower()
    query = [
        (key, val)
        for key, val in parse_qsl(parsed.query, keep_blank_values=True)
        if key.lower() not in TRACKING_QUERY_KEYS and not key.lower().startswith("utm_")
    ]
    return urlunsplit((scheme, netloc, parsed.path or "/", urlencode(sorted(query)), ""))
```

URL 规范化是最低成本的去重手段。只要 canonical URL 相同，就可以认为是同一个详情页。

## 正文清洗

网页正文常见噪声包括：

- 打印本页。
- 关闭窗口。
- 友情提示。
- 免责声明。
- 版权信息。

`clean_text()` 统一移除这些噪声：

```python
def clean_text(value: str) -> str:
    text = value.replace("\xa0", " ")
    for pattern in NOISE_PATTERNS:
        text = re.sub(pattern, " ", text, flags=re.IGNORECASE)
    text = re.sub(r"\s+", " ", text)
    return text.strip()
```

这一步不会改写事实，只删除模板噪声和空白。

## 标题归一化

标题中的公告类型后缀会干扰相似度判断：

```text
上海某医院医疗设备采购项目公开招标公告
上海某医院医疗设备采购项目招标公告
```

`normalize_title()` 会删除常见后缀和标点：

```python
def normalize_title(value: str) -> str:
    text = clean_text(value)
    for suffix in TITLE_SUFFIXES:
        text = text.replace(suffix, "")
    text = re.sub(r"[【】\[\]（）()《》<>「」『』,，.。:：;；!！?？\s_\-]+", "", text)
    return text.lower()
```

归一化后的标题用于 exact match 和相似度计算，不直接展示给用户。

## 项目编号优先

项目编号比标题更可靠。P7 用规则提取：

```python
PROJECT_NO_PATTERNS = (
    r"(?:项目编号|项目代码|招标编号|采购编号|项目号|采购计划编号)\s*[:：]\s*([A-Za-z0-9][A-Za-z0-9\-_/（）()第号\.]{3,80})",
    r"(?:编号)\s*[:：]\s*([A-Za-z0-9][A-Za-z0-9\-_/（）()第号\.]{3,80})",
)
```

如果两条公告都有项目编号，并且编号一致，就直接合并。

## SimHash 的作用

SimHash 用来判断文本近似重复。P7 的 `simhash64()` 把中文字符 bigram 和英文数字 token 映射到 64 位签名：

```python
def simhash64(text: str) -> str:
    tokens = _tokens(text)
    weights = [0] * 64
    for token in tokens:
        digest = int(hashlib.sha1(token.encode("utf-8")).hexdigest()[:16], 16)
        for bit in range(64):
            weights[bit] += 1 if digest & (1 << bit) else -1
```

两个文本越相似，SimHash 的汉明距离通常越小。P7 只在标题相似、发布日期相同的情况下再看 SimHash，避免误合并。

## 聚类判断顺序

`_same_cluster()` 的判断顺序是保守的：

```python
if left_project and right_project and left_project == right_project:
    return True
if canonical_url 相同:
    return True
if title_norm 相同 and 发布日期相同:
    return True
if 发布日期不同:
    return False
if title_similarity < 0.86:
    return False
return hamming_distance <= 10
```

这个顺序的核心是降低误合并风险。招投标场景里，把两个不同项目合并到一起比漏合并更危险。

## cluster_key 如何生成

合并后的公告会有一个稳定 `cluster_key`：

```python
if project and len(cluster) > 1:
    return f"project:{project.lower()}"
if len(cluster) > 1:
    return f"title:{_sha1_short(title + ':' + date)}"
return existing_source_key
```

为什么单条公告保留原 source key？因为前面阶段的 `sent_history` 已经以 `source_site:id` 作为稳定账本键。P7 只在确实发生跨源合并时改用实体级 key。

## runner 如何接入

`runner.collect()` 现在先采集，再清洗聚类：

```python
notices = source_adapter.collect(...)
collected_count = len(notices)
dedup_result = clean_and_cluster_notices(notices)
notices = dedup_result.notices
deduped_count = len(notices)
_persist_notices_and_clusters(settings, notices)
context.emit_tool_call("pipeline.clean_dedup", dedup_result.stats)
```

然后才执行订阅增量：

```python
if subscription_id and incremental:
    cluster_keys = [_cluster_key(notice.to_dict()) for notice in notices]
    unsent = unsent_cluster_keys(...)
```

顺序很重要。先聚类，再查 `sent_history`，才能保证同一项目的跨源重复不会被当成多条新增内容。

## 入库结构

P7 使用已有两张表：

`notices`：

- `id`：`source_site:id`。
- `source_url`：原始来源链接。
- `canonical_url`：规范化链接。
- `content_text`：清洗后的正文。
- `fields_json`：cluster_key、title_norm、project_no、simhash64 等结构化字段。

`clusters`：

- `cluster_key`：聚类主键。
- `primary_notice_id`：主公告。
- `project_no`：项目编号。
- `title_norm`：归一化标题。
- `related_sources_json`：关联来源列表。

这两张表让后续证据链、人工审核和增量推送都有持久基础。

## 报告如何展示关联来源

报告表格中的来源现在使用：

```python
def _source_display(notice: Notice) -> str:
    value = notice.fields.get("source_sites")
    if isinstance(value, list) and value:
        return "、".join(str(item) for item in value)
    return notice.source_site
```

如果两条跨源公告被合并，报告里会显示多个来源，而不是只显示主公告来源。

## 你需要掌握的关键概念

1. 清洗不是总结，不能改写事实。
2. URL 规范化可以解决一部分重复，但不能解决转载。
3. 项目编号是强业务键，优先级高于标题相似度。
4. SimHash 是近似重复判断工具，不能单独决定合并。
5. 聚类必须先于订阅增量，否则同一项目的跨源转载会重复推送。
6. 保守去重比激进去重更适合招投标场景。
