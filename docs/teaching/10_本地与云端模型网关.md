# 10 本地与云端模型网关

## 本阶段解决什么问题

前面几个阶段已经能用规则解析用户问题，并抓取、清洗、去重、生成 Word。规则解析稳定、可控，但遇到同义词、行业别名、采购场景变体时，搜索词可能不够丰富。

P10 引入模型增强，但边界很清楚：

- 规则解析仍然是主链路。
- 模型只补充搜索词和排除词。
- 模型失败不影响主流程。
- 所有模型行为可追踪、可关闭、可审计。

这是一种工业落地里更稳的 AI 接入方式：让模型提升召回，而不是让模型接管关键约束。

## 源码地图

- `tendertrace/llm/gateway.py`：统一封装 Ollama 和 OpenAI 调用。
- `tendertrace/llm/enhancer.py`：把模型 JSON 建议应用到 BidQL。
- `tendertrace/llm/audit.py`：模型审计入库。
- `tendertrace/config.py`：模型模式、超时、模型名和 API 风格配置。
- `tendertrace/runner.py`：在状态图 `intent` 节点中接入模型。
- `tendertrace/db.py`：新增 `model_audits` 表。
- `tests/test_llm_gateway.py`：验证本地/云端请求格式。
- `tests/test_llm_enhancer.py`：验证模型建议的保守采纳。

## 为什么要有 ModelGateway

如果直接在 runner 里写 OpenAI 或 Ollama 请求，后续会出现三个问题：

1. runner 会变得难测。
2. 本地模型和云端模型切换会污染业务代码。
3. 错误处理、脱敏、JSON 解析会散落在多个地方。

所以 P10 新增：

```python
class ModelGateway:
    def __init__(self, settings: Settings, transport: ModelTransport | None = None) -> None:
        self.settings = settings
        self.transport = transport or HttpxModelTransport()
```

这里的关键设计是 `transport` 可注入。正式运行使用 `HttpxModelTransport`，测试时传 `FakeTransport`，这样单元测试不需要真实网络。

## ModelTransport 协议

网关依赖一个很小的协议：

```python
class ModelTransport(Protocol):
    def post_json(
        self,
        url: str,
        *,
        headers: dict[str, str],
        payload: dict[str, Any],
        timeout: float,
    ) -> dict[str, Any]: ...
```

这段代码的重点不是“抽象得很高级”，而是把网络边界切出来。测试可以检查：

- 请求打到哪个 URL。
- header 是否正确。
- payload 是否符合本地或云端接口。
- 没有真实访问 OpenAI 或 Ollama。

## 默认为什么不开启模型增强

默认配置：

```env
TENDERTRACE_MODEL_MODE=local
TENDERTRACE_MODEL_ENHANCEMENT_ENABLED=false
```

本地模式默认是 Ollama，但增强默认关闭。原因很实际：很多机器没有安装或启动 Ollama。如果默认就调用，会让一次普通采集因为本地模型不可用而变慢。

网关入口先做短路判断：

```python
if not self.settings.model_enhancement_enabled:
    return self._result(status, started, "skipped", error="model enhancement disabled")
```

这就是“能力存在，但默认不影响主流程”。

## 本地 Ollama 请求

本地模型调用：

```python
url = f"{self.settings.ollama_base_url.rstrip('/')}/api/chat"
payload={
    "model": self.settings.ollama_model,
    "messages": [
        {"role": "system", "content": system},
        {"role": "user", "content": user},
    ],
    "format": "json",
    "stream": False,
}
```

几个关键点：

- `/api/chat` 是 Ollama 的聊天接口。
- `format: "json"` 要求模型尽量返回 JSON。
- `stream: False` 简化解析流程。
- timeout 来自 `TENDERTRACE_MODEL_REQUEST_TIMEOUT`。

## 云端 OpenAI 请求

云端默认使用 Responses API：

```python
url = f"{self.settings.openai_base_url.rstrip('/')}/responses"
payload={
    "model": self.settings.openai_model,
    "instructions": system,
    "input": user,
    "store": False,
}
```

这里的 `store: False` 表示不要求服务端保存这次输入输出。项目也支持旧的 Chat Completions 风格：

```env
TENDERTRACE_OPENAI_API_STYLE=chat_completions
```

切换后会请求：

```text
/chat/completions
```

这样如果后续更换 OpenAI 兼容服务，只需要改配置或网关，不需要改 runner。

## 为什么不在代码里保存 API key

`Settings` 只保存：

```python
openai_api_key_present: bool
```

真正调用时才读取：

```python
def openai_api_key(self) -> str:
    env_files = [
        _read_env_file(self.workspace_root / ".env.local"),
        _read_env_file(self.workspace_root / ".env"),
    ]
    return _first_value("OPENAI_API_KEY", env_files, "")
```

这样 `config-check` 和 `/api/health` 只能看到 key 是否存在，看不到 key 内容。

## JSON 解析为什么要单独处理

模型可能返回三类内容：

1. 纯 JSON。
2. Markdown fenced JSON。
3. 前后夹杂解释文字的 JSON。

所以网关用 `_parse_json_object()` 做容错：

```python
try:
    value = json.loads(cleaned)
except json.JSONDecodeError:
    start = cleaned.find("{")
    end = cleaned.rfind("}")
```

解析失败时返回 `status="failed"`，不会抛出异常中断任务。

## 模型错误为什么要脱敏

网关捕获异常时会调用：

```python
error=_sanitize_error(f"{type(exc).__name__}: {exc}")
```

`_sanitize_error()` 会替换：

- `Bearer ...`
- `sk-...`

这是为了防止某些底层异常把敏感 header 或 key 带进日志。

## enhance_bidql_with_model 做了什么

增强器入口：

```python
def enhance_bidql_with_model(
    settings: Settings,
    bidql: dict[str, Any],
    *,
    run_id: str | None = None,
    gateway: ModelGateway | None = None,
) -> ModelEnhancement:
```

它执行四步：

1. 从 BidQL 构造模型 prompt。
2. 调用 `ModelGateway.generate_json()`。
3. 如果有 `run_id`，写入 `model_audits`。
4. 如果模型返回有效 JSON，保守采纳关键词。

注意：它不会修改原始 `bidql` 对象，而是用 `deepcopy()` 生成增强后的对象。

## Prompt 中只给必要信息

Prompt 只包含这些字段：

```python
payload = {
    "query": bidql.get("query"),
    "topic": bidql.get("topic"),
    "region": bidql.get("region"),
    "time": bidql.get("time"),
    "schedule": bidql.get("schedule"),
}
```

不把数据库内容、附件正文、运行日志或用户凭证放进 prompt。模型增强只需要理解意图，不需要看到后续采集结果。

## 模型输出格式

系统提示要求模型只返回：

```json
{
  "expanded_keywords": [],
  "negative_keywords": [],
  "intent_summary": "",
  "confidence": 0.0
}
```

为什么格式这么窄？

因为越窄越容易验证。模型只影响召回相关字段，不影响时间、地区、发送频率这些硬约束。

## 如何采纳 expanded_keywords

核心逻辑：

```python
expanded.append({"term": term, "weight": 0.72, "origin": "model"})
```

`origin: "model"` 很重要。后续排查时可以区分：

- `domain_dict`：规则词典扩展。
- `model`：模型建议扩展。

如果模型建议和核心词、已有扩展词、已有排除词重复，就不会采纳。

## 如何采纳 negative_keywords

排除词追加到：

```python
topic["negative"]
```

采集适配器会用这些词过滤明显不符合的公告，例如中标、成交、废标、终止等结果类公告。

这里同样去重，避免模型重复给出已有排除词。

## 为什么要过滤不安全 term

`_is_safe_term()` 做了非常简单的过滤：

```python
if not 1 < len(term) <= 32:
    return False
if "\n" in term or "\r" in term or "\t" in term:
    return False
if re.search(r"https?://|www\.|[{}<>]", term, re.IGNORECASE):
    return False
```

这样可以丢弃：

- 过短或过长内容。
- 多行内容。
- URL。
- 像 JSON 或 HTML 的片段。

这不是复杂安全系统，但足够保护当前“关键词追加”场景。

## meta.model_enhancement 的作用

增强后的 BidQL 会写入：

```python
meta["model_enhancement"] = {
    **result.safe_dict(),
    "applied_keywords": applied_keywords,
    "applied_negatives": applied_negatives,
    "intent_summary": "...",
    "confidence": 0.88,
}
```

这样一个 run 的 checkpoint 里可以看到：

- 模型是否调用成功。
- 用了哪个 provider 和 model。
- 实际采纳了哪些词。
- 模型耗时多少。

这对调试非常重要。

## model_audits 表为什么只存哈希

审计落库：

```python
prompt_sha256 = sha256(prompt_text)
response_sha256 = sha256(result.text)
```

表里保存哈希，不保存明文。这样既能证明“这次调用和某份 prompt/response 对应”，又不会把用户查询、模型输出或敏感信息扩散到数据库。

`model_audits` 是运行级审计，不是模型语料库。

## runner 中如何接入

P10 修改的是 `intent` 节点：

```python
context.emit_tool_call("intent.rule_parser", {"query_length": len(state.original_query)})
enhancement = enhance_bidql_with_model(
    settings,
    bidql,
    run_id=state.run_id,
    gateway=model_gateway,
)
context.emit_tool_call("llm.intent_enhancer", {...})
return state.with_updates(intent=enhancement.bidql)
```

注意接入顺序：

1. 规则解析已经在进入 graph 前完成。
2. `start_run()` 先创建 run 记录。
3. graph 执行 `intent` 节点。
4. 增强器写 `model_audits`，外键可以指向已存在的 run。

## 为什么模型失败不抛异常

模型只是增强，不是主流程必要条件。失败时：

```python
if result.status != "ok":
    return ModelEnhancement(
        bidql=_attach_meta(deepcopy(bidql), result, [], []),
        ...
    )
```

BidQL 保持原来的规则结果，采集、证据、报告继续运行。

这符合工业项目的可用性要求：AI 能提升质量，但不能成为单点故障。

## 测试如何避免真实网络

`test_llm_gateway.py` 里使用：

```python
class FakeTransport:
    def post_json(...):
        self.calls.append(...)
        return self.response
```

测试能检查 OpenAI Responses 请求：

```python
self.assertTrue(call["url"].endswith("/responses"))
self.assertFalse(call["payload"]["store"])
```

也能检查 Ollama 请求：

```python
self.assertTrue(call["url"].endswith("/api/chat"))
self.assertEqual(call["payload"]["format"], "json")
```

没有任何测试需要真实 key。

## runner 测试如何证明增强真的生效

runner 测试注入 `FakeModelGateway`：

```python
result = run_once(
    settings=settings,
    query="最近1个月上海服务器招标信息都有哪些",
    adapter=adapter,
    model_gateway=model_gateway,
)
```

然后检查 adapter 收到的 BidQL：

```python
self.assertIn("GPU服务器", model_terms)
self.assertIn("废标", bidql["topic"]["negative"])
```

这证明增强发生在采集前，而不是报告后处理。

## 本阶段你需要掌握的关键概念

1. 模型增强应该有明确边界，不能替代硬规则。
2. 本地/云端模型要通过同一个网关封装，业务层不关心 provider。
3. 测试 AI 功能时，优先测试请求格式、失败降级和采纳策略，不依赖真实外部服务。
4. key 不应该出现在代码、日志、测试输出、数据库或文档中。
5. 模型输出必须结构化，否则无法可靠接入工程系统。
6. 审计表应保存足够排查的信息，但不要保存敏感明文。
