# 13 交付收口与完成度审计

## 本阶段解决什么问题

P13 不继续加功能，而是做最终交付视角的审计。项目到这个阶段已经有代码、报告、文档、测试和验收命令，但还需要回答一个问题：

“赛题每一条要求，现在到底有什么证据证明？”

因此 P13 生成：

- `docs/delivery/交付清单.md`
- `docs/delivery/完成度审计.md`

## 为什么不能直接宣布完成

大型项目容易出现“主要功能都能跑，所以算完成”的错觉。赛题还有两个容易遗漏的交付要求：

1. Demo 演示视频。
2. 至少一个登录站真实登录态。

当前代码已经实现 Demo 脚本和千里马登录态流程，但视频需要录制，千里马需要人工免费会员登录。P13 把这两个点列为人工动作，而不是把它们藏起来。

## 交付清单的作用

`交付清单.md` 面向提交打包：

- 哪些文件属于设计文档。
- 哪些文件属于操作文档。
- 哪些目录是代码。
- 哪些目录是运行产物。
- 哪些本地目录不应入仓。

这能避免最终打包时漏掉关键文档，或把 `.env.local`、`secrets/`、`data/` 带出去。

## 完成度审计的作用

`完成度审计.md` 面向验收解释：

- 每个赛题要求。
- 当前证据。
- 判断结果。

这比简单写“已完成”更有说服力，因为每一项都有文件或命令支撑。

## 为什么把 warning 写进报告

当前 `acceptance-check` 的唯一 warning 是：

```text
source:qianlima login_required
```

这不是代码失败。它表示当前机器还没有保存登录态。正确处理方式是：

- 代码中保留登录态流程。
- 操作文档说明如何登录。
- 完成度审计透明标注“待人工保存”。
- 录制前由用户完成免费会员登录。

## 本阶段你需要掌握的关键概念

1. 完成度审计必须基于证据，不基于记忆。
2. 人工动作和代码缺陷要区分。
3. 最终交付清单应明确哪些文件要交、哪些文件不能交。
4. warning 可以存在，但不能被伪装成 pass。
5. 如果要求真实视频，就必须按 Demo 脚本录制视频文件。
