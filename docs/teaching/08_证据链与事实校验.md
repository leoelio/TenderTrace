# 08 证据链与事实校验

## 本阶段解决什么问题

前面 P7 已经解决了多来源重复公告的问题，但报告仍然需要回答一个更关键的问题：这段“核心内容”凭什么可信？

招投标聚合工具不是普通摘要工具。企业用户会拿报告做项目跟进、采购判断、合规核对，所以每条信息都必须能回到原文：

- 核心内容来自哪一段详情正文。
- 附件链接是否被保留下来。
- 这一条公告的来源链接是什么。
- 如果详情页抓不到正文，系统是否明确提示风险。
- 定时推送时，即使内容不重复，证据也要能入库追踪。

P8 新增的证据链就是为了解决这些问题。

## 源码地图

- `tendertrace/pipeline/evidence.py`：证据链主模块。
- `tendertrace/runner.py`：新增 `evidence` 状态图节点。

- `tests/test_pipeline_evidence.py`：验证证据模块。
- `tests/test_runner.py`：验证证据节点和入库。
- `tests/test_report_writer.py`：验证 Word 展示。

## 为什么证据节点放在 dedup 后面

P8 的顺序是：

```text
adapter.collect -> clean_and_cluster_notices -> attach_evidence -> sent_history incremental -> report
```

不能把证据校验放在适配器内部，因为适配器只负责某一个网站。跨来源合并后，系统才知道最终哪条公告是主公告、有哪些关联来源、最终 `cluster_key` 是什么。

也不能把证据校验放在 Word 写入时才做，因为那样数据库里没有证据记录，后续 UI、审计和增量推送都无法复查。

所以最合适的位置是：P7 去重之后，P5 增量过滤之前。

## EvidenceResult 的作用

`pipeline.evidence` 中先定义了一个简单结果对象：

```python
@dataclass(frozen=True)
class EvidenceResult:
    notices: list[Notice]
    stats: dict[str, object]
```

这个对象有两个职责：

1. 返回带证据字段的新 `Notice` 列表。
2. 返回运行统计，例如检查了多少条、通过多少条、有多少 warning。

这里不用复杂抽象，因为 P8 的输入输出都很明确：输入是 `Notice`，输出还是 `Notice`，只是 `fields` 里多了证据。

## attach_evidence 主流程

核心入口是：

```python
def attach_evidence(notices: list[Notice]) -> EvidenceResult:
    enriched = [_with_evidence(notice) for notice in notices]
    warnings = sum(1 for notice in enriched if notice.fields.get("evidence_status") != "passed")
    return EvidenceResult(
        notices=enriched,
        stats={
            "evidence_checked": len(enriched),
            "evidence_passed": len(enriched) - warnings,
            "evidence_warnings": warnings,
        },
    )
```

这段代码有一个重要设计：它不修改原对象，而是生成新的 `Notice`。原因是 `Notice` 是冻结 dataclass，天然更适合作为不可变数据在状态图里传递。

## 证据包包含什么

每条公告会得到一个 `evidence` 字段：

```python
evidence = {
    "source_url": notice.source_url,
    "canonical_url": canonicalize_url(notice.source_url),
    "snapshot_sha256": snapshot_sha256,
    "excerpt": excerpt,
    "attachments": [_attachment_dict(item) for item in attachments],
    "related_sources": _related_sources(notice),
    "fact_checks": fact_checks,
    "quality_score": quality_score,
    "status": status,
}
```

逐项解释：

- `source_url`：原始公告详情页。
- `canonical_url`：去掉追踪参数后的规范化 URL。
- `snapshot_sha256`：对证据文本做哈希，后续可以判断正文是否变化。
- `excerpt`：报告中可直接展示的证据摘录。
- `attachments`：规范化后的附件列表。
- `related_sources`：跨来源合并后的关联公告来源。
- `fact_checks`：规则型事实校验结果。
- `quality_score`：校验分数。
- `status`：`passed` 或 `warning`。

注意，这里没有让模型“判断真假”。P8 做的是工程可追溯：把来源、摘录、哈希和规则校验记录下来。

## 证据文本如何构造

证据文本来自已有结构化字段：

```python
def _evidence_text(notice: Notice) -> str:
    return clean_text(
        " ".join(
            part
            for part in (
                notice.title,
                notice.publish_time,
                notice.region,
                notice.purchaser,
                notice.content_text,
                notice.core_content,
            )
            if part
        )
    )
```

这不是生成新内容，而是把采集得到的标题、时间、地区、采购人、详情正文、核心内容拼成一个可校验文本。

后续哈希和覆盖率计算都基于这份文本。

## snapshot_sha256 为什么重要

```python
def _sha256(value: str) -> str:
    return hashlib.sha256(value.encode("utf-8")).hexdigest()
```

哈希不是为了加密，而是为了审计：

- 同一来源正文是否发生变化。
- 同一条公告是否被不同运行重复采到。
- 后续如果要做网页快照或 PDF 缓存，可以用哈希作为变化检测依据。

对于招投标场景，公告更正、附件替换、正文修订都可能发生，所以保存哈希有实际价值。

## 证据摘录如何选择

```python
anchors = [
    str(notice.fields.get("project_no") or ""),
    "项目编号",
    "项目概况",
    "预算",
    "采购",
    "招标",
]
```

摘录优先围绕项目编号、项目概况、预算等关键词截取。这样 Word 里的证据摘录更接近用户最关心的信息，而不是随机拿正文开头。

如果没有命中锚点，就退回正文前 420 个字符。

这是一种保守策略：不改写，只截取。

## 事实校验不是 LLM 判断

P8 的 `_fact_checks()` 做四类检查：

```python
checks.append({"field": "source_url", ...})
checks.append({"field": "detail_text", ...})
checks.append({"field": "title", ...})
checks.append({"field": "core_content", ...})
```

含义分别是：

- 来源链接是否是 HTTP/HTTPS。
- 是否抓到了详情正文。
- 标题是否能在证据文本中得到覆盖。
- 核心内容是否被证据文本覆盖。

如果详情正文缺失，状态会变成 `warning`。这比“硬凑一个摘要”更适合工业落地，因为用户能看到风险。

## grounding_score 的意义

核心内容校验使用覆盖率：

```python
def _grounding_score(summary: str, evidence_text: str) -> float:
    if summary and summary in evidence_text:
        return 1.0
    summary_tokens = set(_tokens(summary))
    evidence_tokens = set(_tokens(evidence_text))
    return round(len(summary_tokens & evidence_tokens) / len(summary_tokens), 3)
```

如果核心内容是详情正文的子串，直接得 1.0。

如果不是完全子串，就切成 token 后计算覆盖率。中文使用 bigram，英文数字使用普通 token。

这个方法不能替代专业事实核验，但足够发现一类常见问题：核心内容和原文完全不相关。

## 附件规范化

附件处理有两层：

```python
for attachment in [*notice.attachments, *_inline_attachments(notice)]:
    key = canonicalize_url(attachment.url)
    if not key or key in seen:
        continue
    seen.add(key)
    merged.append(attachment)
```

第一层保留适配器从 HTML `<a>` 标签中提取的附件。

第二层从正文里补充裸链接，例如：

```text
https://example.com/spec.pdf
```

两类附件会按规范化 URL 去重。这样即使 URL 多了 `utm_source`，也不会在报告中重复出现。

## runner 中的新 evidence 节点

P8 后，`collect` 只负责采集和去重：

```python
dedup_result = clean_and_cluster_notices(notices)
notices = dedup_result.notices
context.emit_tool_call("pipeline.clean_dedup", dedup_result.stats)
```

新增的 `evidence` 节点负责校验、持久化和增量过滤：

```python
notices = [_notice_from_dict(item) for item in state.notices]
evidence_result = attach_evidence(notices)
notices = evidence_result.notices
_persist_notices_and_clusters(settings, notices)
context.emit_tool_call("pipeline.evidence_validate", evidence_result.stats)
```

这让状态图更清晰：

- `collect`：拿数据。
- `evidence`：证明数据。
- `report`：输出数据。

## 为什么持久化早于增量过滤

在 `evidence` 节点里，系统先调用：

```python
_persist_notices_and_clusters(settings, notices)
```

然后才检查：

```python
if subscription_id and incremental:
    unsent = unsent_cluster_keys(...)
```

原因是：即使一条公告已经推送过，本轮采集到它也仍然是有价值的运行证据。报告可以不重复发，但数据库应该知道系统本轮再次看到了它。

## evidence_items 表

P8 新增：

```python
CREATE TABLE IF NOT EXISTS evidence_items (
    id TEXT PRIMARY KEY,
    notice_id TEXT NOT NULL,
    cluster_key TEXT NOT NULL,
    source_site TEXT NOT NULL,
    source_url TEXT NOT NULL,
    snapshot_sha256 TEXT NOT NULL,
    excerpt TEXT NOT NULL,
    attachments_json TEXT NOT NULL DEFAULT '[]',
    fact_checks_json TEXT NOT NULL DEFAULT '[]',
    quality_score REAL NOT NULL DEFAULT 0
)
```

这张表是证据账本。它和 `notices.fields_json` 的区别是：

- `fields_json` 方便报告直接使用。
- `evidence_items` 方便审计、查询和后续 UI 展示。

## Word 报告如何展示证据

报告详情里新增：

```python
if evidence:
    _add_label_value(doc, "事实校验", _evidence_status_text(notice))
    _add_label_value(doc, "证据哈希", str(evidence.get("snapshot_sha256") or "无"))
    _add_label_value(doc, "证据摘录", str(evidence.get("excerpt") or "无"))
```

这三个字段对应三个验收问题：

- `事实校验`：这条内容是否有明显证据风险。
- `证据哈希`：详情正文证据是否可追踪。
- `证据摘录`：用户能否直接看到原文依据。

## 测试如何证明 P8 生效

P8 增加或更新了三类测试。

第一类是证据模块测试：

```python
result = attach_evidence([notice])
self.assertEqual(result.stats["evidence_checked"], 1)
self.assertEqual(enriched.fields["evidence_status"], "passed")
self.assertEqual(len(evidence["snapshot_sha256"]), 64)
```

第二类是 runner 测试：

```python
self.assertEqual(
    [checkpoint.node for checkpoint in checkpoints],
    ["intent", "collect", "evidence", "report"],
)
self.assertEqual(len(evidence_rows), 1)
```

第三类是 Word 测试：

```python
self.assertIn("事实校验：passed（score: 1.0）", text)
self.assertIn("证据摘录：项目概况", text)
```

这三类测试分别覆盖算法、编排和交付物。

## 本阶段你需要掌握的关键概念

1. 证据链不是摘要，它是来源、正文、附件、哈希、校验结果的组合。
2. 事实一致性第一步不是用大模型判断，而是先保证核心内容能被原文覆盖。
3. `warning` 比沉默失败更重要，因为它告诉用户这一条需要人工复核。
4. 证据应当在报告前入库，而不是只存在于 Word 文件里。
5. 去重、证据、增量过滤三者顺序不能随意换。
6. 工业系统要能解释“为什么这条信息可信”，而不只是“我给你总结了什么”。
