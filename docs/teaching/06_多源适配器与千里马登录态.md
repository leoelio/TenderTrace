# 06 多源适配器与千里马登录态

## 本阶段解决什么问题

P6 解决赛题中的来源覆盖要求。前面阶段已经能从一个公开源抓取、生成 Word、订阅增量推送，但真实验收要求至少两个来源，并且至少一个来源需要登录后获取信息。

本阶段做了三件事：

- 新增全国公共资源交易平台 `ggzy` 适配器。
- 新增 `MultiSourceAdapter`，让默认运行从单源变成多源。
- 新增千里马 `storage_state` 登录态管理，后续可以接入免费会员可见页面。

## GGZY 适配器为什么用接口而不是解析页面

全国公共资源交易平台的 `dealList.html` 是一个 Vue 页面壳。列表数据不是直接写在 HTML 里，而是浏览器通过 POST 请求加载：

```text
POST /information/pubTradingInfo/getTradList
```

适配器没有猜接口，而是按页面里的 `getList()` 逻辑构造同样的表单参数：

```python
def build_search_body(bidql: dict[str, Any], *, page: int = 1) -> dict[str, str]:
    body = {
        "SOURCE_TYPE": "1",
        "PAGENUMBER": str(page),
    }
    window = bidql.get("time", {}).get("resolved_window")
    if isinstance(window, dict) and window.get("from") and window.get("to"):
        body["TIMEBEGIN"] = str(window["from"])
        body["TIMEEND"] = str(window["to"])
    else:
        body["DEAL_TIME"] = "02"
    adcode = bidql.get("region", {}).get("adcode")
    if adcode:
        body["DEAL_PROVINCE"] = str(adcode)
    keyword = _topic_keyword(bidql)
    if keyword:
        body["FINDTXT"] = keyword
    return body
```

这里的设计原则是：能用站点公开请求接口，就不要用浏览器硬点页面。接口返回 JSON，字段结构稳定，测试也更容易写。

## 记录如何变成 Notice

GGZY 返回的每条 record 需要转成系统统一的 `Notice`：

```python
Notice(
    id=notice_id,
    source_site="ggzy",
    title=title,
    publish_time=record["publishTime"],
    region=province,
    purchaser=platform or province,
    source_url=source_url,
    fields={
        "cluster_key": f"ggzy:{notice_id}",
        "business_type": business_type,
        "information_type": information_type,
        "platform": platform,
        "raw": record,
    },
)
```

统一对象的好处是报告生成器、订阅增量、去重逻辑都不需要知道来源差异。它只处理 `Notice`。

`cluster_key` 很重要。订阅增量阶段会用它写入 `sent_history`。如果 key 不稳定，同一条公告下次运行会被当成新公告，造成重复推送。

## 详情页为什么需要两次请求

GGZY 的列表 record 指向的是 `html/a/...` 页面。这个页面通常是一个交易阶段容器，正文详情在 `html/b/...` 页面里。适配器先抓容器页，再从 `showDetail()` 中提取正文路径：

```python
def _detail_body_path(html: str) -> str | None:
    match = re.search(r"showDetail\([^)]*'(?P<path>/information/deal/html/b/[^']+\.html)'", html)
    return match.group("path") if match else None
```

然后抓正文页，清理脚本和样式：

```python
def _extract_content(parser: HTMLParser) -> str:
    node = parser.css_first("#mycontent") or parser.css_first(".detail_content") or parser.css_first(".detail")
    if node is None:
        return ""
    for bad in node.css("script,style"):
        bad.decompose()
    return _clean_spaces(node.text(separator=" "))
```

这样报告中的核心内容来自真实详情页正文，不是模型生成。

## MultiSourceAdapter 的职责

`MultiSourceAdapter` 不负责具体抓网页。它只负责调度多个来源：

```python
class MultiSourceAdapter:
    def __init__(self, adapters: list[SourceAdapter]) -> None:
        self.adapters = adapters
        self.last_source_stats: list[SourceRunStat] = []
```

默认来源：

```python
adapters: list[SourceAdapter] = [CcgpAdapter(), GgzyAdapter()]
if vault.has_storage_state():
    adapters.append(QianlimaAdapter(vault=vault))
```

这意味着没有千里马登录态时，系统仍然能稳定使用两个公开源；用户完成千里马登录后，登录源会自动进入默认采集器。

## 为什么单源失败不能中断全部运行

真实互联网采集里，某个站点临时失败很常见。多源系统不能因为一个源触发验证码或超时，就丢掉其他源的结果。

聚合器捕获单源异常：

```python
try:
    notices = adapter.collect(bidql, max_pages=max_pages, max_results=max_results)
except Exception as exc:
    self.last_source_stats.append(
        SourceRunStat(
            source=source_name,
            status="failed",
            error=f"{type(exc).__name__}: {exc}",
        )
    )
    results_by_source.append([])
    continue
```

失败会进入 `source_stats`，但其他来源继续执行。这样 trace 和 runlog 可以证明问题来自哪个外部站点，而不是系统硬编码或整体失败。

## 为什么结果用 round-robin 合并

如果简单把 CCGP 的结果全部放前面，`max_results=4` 时可能 4 条都来自第一个源，第二源虽然抓到了也进不了报告。

P6 使用 round-robin：

```python
def _round_robin(results_by_source: list[list[Notice]], limit: int) -> list[Notice]:
    merged: list[Notice] = []
    index = 0
    while len(merged) < limit:
        added = False
        for notices in results_by_source:
            if index < len(notices):
                merged.append(notices[index])
                added = True
                if len(merged) >= limit:
                    break
        if not added:
            break
        index += 1
    return merged
```

这样在多个来源都有结果时，报告更容易体现多源覆盖。

## 千里马为什么只保存 storage_state

用户明确要求不要在代码中保存账号密码。Playwright 的 `storage_state` 是更合适的机制：

```python
context.storage_state(path=str(self.storage_state_path))
```

登录流程：

```python
browser = playwright.chromium.launch(headless=False)
context = browser.new_context()
page = context.new_page()
page.goto(QIANLIMA_HOME_URL, wait_until="domcontentloaded")
input("请在打开的浏览器中完成千里马登录，然后回到终端按 Enter 保存登录态...")
context.storage_state(path=str(self.storage_state_path))
```

这段代码的意义是：

- 浏览器可见，用户自己输入账号密码和验证码。
- 程序只在登录完成后保存浏览器状态。
- `secrets/` 已经被 `.gitignore` 忽略。
- `source-status` 不打印 Cookie 内容。

## 意图解析里的一个真实问题

真实烟测时发现，“最近10天全国设备招标信息都有哪些”最初被解析成主题 `全国设备`。这会导致 GGZY 搜索关键词过窄，返回 0 条。

修复方式是把 `全国` 加入 topic 停用短语：

```python
_STOP_PHRASES = [
    "全国范围",
    "全国",
    ...
]
```

并补测试：

```python
self.assertEqual(bidql["topic"]["core"], ["设备"])
self.assertIsNone(bidql["region"]["province"])
```

这个例子说明：外部烟测不是走形式，它会发现单元测试没覆盖到的真实表达。

## 你需要掌握的关键概念

1. 适配器负责把不同网站转换成统一 `Notice`。
2. 聚合器不解析页面，只负责编排多个适配器。
3. 多源系统必须允许单源失败，并把失败写入可审计状态。
4. 登录站不要保存账号密码，使用人工登录 + `storage_state`。
5. `cluster_key` 必须稳定，否则订阅增量会重复推送。
6. 真实烟测用于发现规则解析和站点接口的真实边界，不能只依赖夹具。
