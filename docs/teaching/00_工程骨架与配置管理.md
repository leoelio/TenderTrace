# 00 工程骨架与配置管理

## 本阶段解决什么问题

P0 的任务是给后续所有模块提供稳定地基：项目可以安装、配置可以被安全读取、运行目录可以自动创建、SQLite 可以幂等建表、健康接口可以被 UI 和演示脚本检查。

这一步故意不写采集逻辑。原因很简单：如果配置、数据库和启动方式不稳定，后面每个 Agent 都会把问题放大。

## 源码地图

- `.gitignore`：忽略密钥、登录态、数据库、报告、快照、前端构建产物和 Word 临时文件。
- `.env.example`：本地配置模板，包含 Web + outbox 发送渠道、Ollama 本地模式、OpenAI 云端模式。
- `pyproject.toml`：Python 包与依赖声明，提供 `tendertrace` 命令入口。
- `tendertrace/config.py`：读取 `.env.local`、`.env` 和系统环境变量，生成 `Settings`。
- `tendertrace/db.py`：SQLite 连接、WAL 配置、核心表 DDL、健康检查。
- `tendertrace/cli.py`：`init-db`、`config-check`、`health`、`serve` 四个命令。
- `tendertrace/app/api.py`：FastAPI 应用工厂，提供健康检查和 outbox 下载接口。
- `tendertrace/scheduling/ledger.py`：`sent_history` 增量幂等的最小实现。
- `tests/`：用标准库 `unittest` 验证配置、建表和增量去重。

## 配置设计

配置读取顺序是：系统环境变量优先，其次 `.env.local`，最后 `.env`，再使用默认值。

这样做有两个好处：

1. 本地开发可以用 `.env.local`，不会进仓库。
2. 部署或评测时可以用系统环境变量覆盖，不需要改文件。

`Settings.safe_summary()` 是专门给日志、健康接口和 UI 用的安全摘要。它只输出 `openai_key_configured` 这种布尔值，不输出 Key 原文。

## 为什么不用更复杂的配置框架

P0 使用标准库手写一个很小的 `.env` 读取器，而不是引入 Pydantic Settings。原因是当前阶段只需要十几个配置项，手写逻辑更透明，也减少启动失败点。后续如果配置校验变复杂，再引入 Pydantic Settings 不晚。

## 数据库设计

P0 一次性创建核心表，但不实现全部业务：

- `subscriptions`：订阅任务。
- `runs`：每次执行轮次。
- `notices`：公告条目。
- `clusters`：去重后的项目簇。
- `sent_history`：增量推送账本。
- `adapter_registry`：站点适配器版本。
- `trace_events`：Agent 事件流。
- `outbox_messages`：本地 outbox 报告记录。

其中 `sent_history` 的主键是 `(subscription_id, cluster_key)`。这就是“不重复推送”的数据库级保证：同一个订阅下，同一个项目簇只能被记账一次。

## 关键代码解释

`Settings.load()` 完成三件事：

1. 读取环境变量和 env 文件。
2. 校验端口、模型模式等关键字段。
3. 把相对路径转换成工作区下的绝对路径。

`init_db()` 是幂等的。它使用 `CREATE TABLE IF NOT EXISTS` 和 `INSERT OR IGNORE`，所以重复执行不会破坏已有数据。

`mark_sent()` 使用 `INSERT OR IGNORE` 写入 `sent_history`。第一次写入返回 `True`，重复写入返回 `False`。后续订阅 Agent 会用这个返回值决定一条公告是否进入本轮 Word。

## 验证方法

运行：

```powershell
python -m unittest discover -s tests
```

重点看三个测试：

- 默认配置必须是本地 Ollama 模式。
- 云端模式没有 `OPENAI_API_KEY` 时必须启动失败。
- 同一订阅同一项目簇重复写入 `sent_history` 时，第二次必须失败。
