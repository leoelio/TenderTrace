# TenderTrace 详设文档

文档版本：v2.3（对应代码阶段 P27）

## 1. 项目定位

TenderTrace 是一个面向招投标情报聚合的可运行系统。用户输入自然语言问题后，系统解析主题、区域、时间范围和调度意图，优先从本地公告库检索，不足时从多个互联网招投标来源现场补采，执行清洗、去重、附件抽取、证据校验和 Word 汇总，并通过 Web 下载、本地 outbox 与可选 SMTP 邮件交付。

系统目标不是只完成一次搜索，而是支持持续关注：

- 如果用户问题包含发送时间和频率，系统创建定时订阅；订阅再次触发时通过 `sent_history` 保证只推送新增项目。
- 后台采集任务（ingest）按主题池与地区池周期性抓取入库，持续扩充本地检索语料，使查询“越用越全、越用越快”。

## 2. 需求覆盖

### 2.1 输入能力

系统支持自然语言问题，例如：

- 最近1个月的安徽省区域内的服务器招标信息都有哪些
- 最近3个月苏州服务器采购招标公告
- 最近6个月成都医疗设备招标信息有哪些
- 最近3个月的上海区域内的充电桩招标信息都有哪些，请汇总后每天9:00发送给我

解析输出为 BidQL，中间表示包含：

- `topic.core`：核心主题词（三层抽取：品类词典 → 词性过滤 → 规则兜底）。
- `topic.expanded`：词典或模型扩展词（带权重与来源标记）。
- `topic.negative`：排除词（中标、成交、废标等结果类公告）。
- `region`：省、市、区三级，含 adcode 与别名表；支持全国全部区县。
- `time.resolved_window`：时间 AST 按运行时 `now` 求值后的起止时间。
- `schedule`：立即执行、一次性定时、周期性调度。
- `delivery`：Web 下载、outbox 与可选 email。
- `meta`：置信度、澄清需求（`clarify_needed`）、模型增强审计摘要。

### 2.2 输出能力

系统生成 `.docx` 报告，文件名遵循：

```text
{用户的问题}_{yyyyMMddHHmm}.docx
```

报告逐条包含：标题、发布时间、来源链接、核心内容、附件链接、附件正文摘录、证据摘录与事实校验结果、地域降级说明（如发生）。

## 3. 总体架构

```text
CLI / Web UI
  -> FastAPI（24 个 REST 端点）
  -> TenderGraph
      -> intent    （规则编译 + LLM 可选增强）
      -> collect   （本地检索优先 -> 不足则多源补采 -> 清洗去重聚类）
      -> evidence  （附件抽取 -> 证据链 -> 增量账本过滤）
      -> report    （Word 生成 -> outbox 投递 -> mark_sent）
  -> SQLite / FTS5 / outputs / outbox

后台数据流（与查询解耦）：
APScheduler(ingest cron / ingest_subscriptions)
  -> 主题池 x 地区池 合成查询
  -> MultiSourceAdapter 采集
  -> 清洗去重 -> notices 入库 -> notices_fts 同步 -> (可选) notice_embeddings
```

核心持久化：

- `runs` / `trace_events` / `run_checkpoints`：运行、事件流、节点检查点。
- `subscriptions` / `ingest_subscriptions`：用户报告订阅与后台采集订阅（分离管理）。
- `sent_history`：增量推送账本。
- `notices` / `clusters`：公告与项目簇。
- `notices_fts`：FTS5 全文索引虚表（jieba 分词）。
- `notice_embeddings`：可选向量索引（模型、维度、text_sha256 增量键）。
- `evidence_items` / `attachment_snapshots`：证据项与附件快照。
- `model_audits` / `outbox_messages` / `adapter_registry` / `schema_migrations`。

## 4. 核心模块设计

### 4.1 配置管理

文件：`tendertrace/config.py`

系统从环境变量、`.env.local` 和 `.env` 读取配置。敏感信息不进入 `safe_summary()`，OpenAI key 和 SMTP password 只暴露是否配置。P26 配置组：

```env
TENDERTRACE_INGEST_ENABLED=false      # 后台采集开关
TENDERTRACE_INGEST_CRON=0 */6 * * *   # 采集频率
TENDERTRACE_INGEST_TOPICS=...         # 主题池（CSV）
TENDERTRACE_INGEST_REGIONS=...        # 地区池（CSV）
TENDERTRACE_VECTOR_ENABLED=false      # 向量检索开关
TENDERTRACE_VECTOR_MODEL=...          # 嵌入模型名
TENDERTRACE_VECTOR_TOP_K=...          # 向量召回条数
TENDERTRACE_DELIVERY_CHANNELS=web,outbox,email
TENDERTRACE_SMTP_HOST=smtp.example.com
TENDERTRACE_SMTP_USERNAME=...
TENDERTRACE_SMTP_PASSWORD=...
TENDERTRACE_SMTP_FROM=sender@example.com
TENDERTRACE_SMTP_TO=receiver@example.com
```

### 4.2 BidQL 意图解析

文件：

- `tendertrace/intent/compiler.py`
- `tendertrace/intent/time_expr.py`
- `tendertrace/intent/region.py`
- `tendertrace/intent/admin_divisions.py`
- `tendertrace/intent/schedule.py`
- `tendertrace/intent/topic.py`

解析过程先走确定性规则。相对时间保存为 AST，运行时按 `now` 求值，保证“最近3个月”在不同日期下可复现。

区域解析（P23 升级）：`admin_divisions.py` 内置全国省、市、区三级行政区划数据（数据源 province-city-china，含 adcode），`parse_region` 按区 → 市 → 省逐级做最长别名匹配，输出省/市/区、adcode 与别名表。检索时按区级 → 市级 → 省级逐级过滤。

主题抽取（P23 升级）为三层策略：

1. 品类同义词典优先：内置充电桩、服务器、空调、储能、医疗设备、电梯、消防、安防、网络设备等九大采购品类的同义词组，命中即产出核心词与扩展词；
2. 词性过滤：`jieba.posseg` 分词后保留名词、动名词、英文词元，剔除停用词；
3. 规则兜底：停用短语剔除后的启发式提取。

模型只作为增强项，不能覆盖规则解析出的地区、时间和调度。

### 4.3 TenderGraph 编排器

文件：`tendertrace/runtime/{graph,state,bus,checkpoint,trace}.py`

TenderGraph 负责节点执行、条件路由、检查点保存和事件发布。每个节点执行时写入 `node_started`、`tool_called`、`node_finished`、`run_finished` 事件；节点完成后完整 `RunState` 序列化写入 `run_checkpoints`，支持 `resume=True` 断点续跑。`add_conditional_edge` 与 `RunState.repair_rounds` 为反思循环预留，当前主链路为线性四节点。

### 4.4 本地检索（P22/P23 新增）

文件：`tendertrace/retrieval.py`、`tendertrace/vector.py`

`search_notices` 是在线检索入口，实现“本地优先”的第一级检索：

- FTS5 通道：`notices_fts` 虚表以 `jieba.lcut_for_search` 分词入索引；查询词元按 OR 匹配，`bm25(notices_fts, 8.0, 1.0)` 标题加权排序；FTS5 不可用时自动降级为 LIKE 匹配。
- SQL 内联过滤：发布时间窗（`resolved_window`）、区划别名（区级 → 市级 → 省级）、负向词排除。
- 城市降级：城市级检索零命中时放宽到省级二次检索，结果标记 `relaxed_city` 并在 UI 与报告中披露。
- 向量通道（可选）：`sentence-transformers` 对公告全文建嵌入（`notice_embeddings`，按 `text_sha256` 与模型名双键增量构建）；查询向量余弦相似召回，与词法结果按 RRF（k=60）融合。默认关闭，需安装 `.[vector]` extra；依赖缺失时返回 `unavailable` 并静默降级。

`runner.collect` 节点的两级策略：本地命中数达到 `max_results` 时可秒级返回；如果默认多源适配器发现本地缓存只覆盖单一来源，则继续触发公开源补采，优先形成至少两个外部来源的尝试证据。补采结果与本地结果合并后进入清洗去重，并同步入库回流，形成语料正反馈。

### 4.5 后台采集（P22/P23 新增）

文件：`tendertrace/ingest.py`、`tendertrace/scheduling/ingest_subscriptions.py`

`run_ingest_cycle` 按主题池 x 地区池合成查询（如“最近30天上海充电桩招标信息”），经 `MultiSourceAdapter` 采集、清洗去重后调用 `persist_notices_and_clusters` 入库并同步 FTS 索引。三种触发方式：

1. 全局 Cron（`TENDERTRACE_INGEST_ENABLED` + `TENDERTRACE_INGEST_CRON`）；
2. 采集订阅 `ingest_subscriptions`（与用户报告订阅分离，独立 CRUD 与手动触发）；
3. CLI `ingest-once --topic ... --region ...` 手动预热。

### 4.6 多源采集与托管抓取

文件：`tendertrace/adapters/{ccgp,ggzy,multi}.py`、`tendertrace/fetching.py`、`tendertrace/linking.py`、`tendertrace/source_map.py`

`SourceAdapter` 协议：`collect(bidql, max_pages, max_results) -> list[Notice]`。CCGP 与 GGZY 为公开 HTTP 源（httpx + selectolax），GGZY 含长时间窗兜底。`MultiSourceAdapter` 聚合各源：单源异常仅记录 `SourceRunStat` 不中断整体；各源结果按 `cluster_key` 去重后轮询合并，保证来源多样性。

P25 将 Scrapling/Firecrawl 的可借鉴部分落到工程链路里：

- `ManagedFetcher` 统一 User-Agent、重试、阻断识别、错误统计和批量详情抓取；详情页按输入顺序回填，降低多条公告串行请求耗时。
- `PageArtifact` 保存 fetcher、状态码、耗时、最终 URL、内容长度、正文选择器、fallback 与摘要，便于回溯“这个结论来自哪次页面抓取”。
- `LinkExtractor` 提供 URL Map 能力：按来源声明 allow/deny、同域限制和附件扩展名，避免每个适配器重复写临时链接规则。
- `/api/source-map` 与数据源页展示入口路由、发现规则和近次来源健康，包括请求数、成功率、阻断、重试和页面快照数。
- P26 起 `acceptance-check` 不只看最终命中来源，也会审计运行统计中的外部来源尝试证据（multi-source attempt evidence），避免因主题/时间窗只命中单站而误判多源能力缺失。

### 4.7 登录态管理

文件：`tendertrace/vault/qianlima.py`

千里马为登录态源。`login-qianlima` 打开可见浏览器由人工合规登录，Playwright `storage_state` 保存至 `secrets/`；`verify-qianlima` 输出结构化会话校验（cookie/origin 计数、有效性判定），不暴露 cookie 内容。会话失效时公开源运行不受影响。不做验证码识别，不保存密码。

P25 增强后，千里马不再只停留在搜索页候选：登录态搜索页解析候选公告后，会继续进入详情页，复用 `select_main_content` 做正文选择，抽取标题、发布时间、地区、采购人和附件链接，并记录 Playwright 抓取统计。若登录态失效或详情页受限，运行统计会标出 blocked/last_error，但不会拖垮公开源。

### 4.8 清洗、去重与聚类

文件：`tendertrace/pipeline/dedup.py`

四级判重逐级兜底：

1. 项目编号相同（正则抽取采购/招标编号）；
2. 规范化 URL 相同（剥离 utm/spm 等跟踪参数）；
3. 标题归一相同且同日发布（去公告类型后缀、去标点、转小写）；
4. 近重复：同日发布 + 标题字符二元组 Jaccard >= 0.86 + 全文 simhash64 汉明距离 <= 10。

同簇合并保留正文最长者为主记录，合并附件（按规范化 URL 去重），`related_sources` 保留全部来源出处；`cluster_key` 同时是增量推送判重键。

### 4.9 附件下载与正文抽取

文件：`tendertrace/pipeline/attachments.py`

受限下载：每公告最多 3 个附件、单个最大 8MB、超时 8 秒；PDF/DOCX/XLSX 抽取正文；产出 `attachment_snapshots` 记录（sha256、字节数、文本摘录、错误原因）。下载器协议化可注入，测试不出网。

### 4.10 证据链与事实校验

文件：`tendertrace/pipeline/evidence.py`

每条公告生成证据对象：`source_url`、`canonical_url`、`snapshot_sha256`（正文快照哈希）、`excerpt`、附件快照、`fact_checks`（链接合法性、正文非空、时间格式、附件可回指等逐项打分）与 `quality_score`。未全部通过者标记 `warning` 并在报告中如实展示。证据项持久化至 `evidence_items`。

结构化字段抽取（项目编号、预算金额、投标截止、开标时间）同时生成字段级证据：`value`、`evidence_text`、`source_url`、`confidence`。Word 报告会展示字段证据片段，减少“LLM 总结但证据不清”的风险。

### 4.11 模型网关

文件：`tendertrace/llm/{gateway,enhancer,audit,doctor}.py`

统一封装本地 Ollama（`/api/chat`，`format=json`）与 OpenAI 兼容云端（responses 与 chat completions 双风格，temperature=0）。运行时策略 `config/rules/local/cloud/hybrid` 按次切换。增强约束：模型仅可追加扩展词与负向词（白名单校验：长度 2-32、禁 URL/尖括号/换行、上限 8 个、不与负向词冲突），不可覆盖规则槽位；每次调用写 `model_audits`（仅记录 parsed_keys 与延迟，不落原文）；错误信息正则脱敏（Bearer token、sk- 前缀密钥打码）；失败静默降级为纯规则。`model-doctor` 提供连通性自检并保证云端模式与本地 Ollama 依赖隔离。

### 4.12 定时任务与增量推送

文件：`tendertrace/scheduling/{scheduler,subscriptions,ledger}.py`

APScheduler 承载两类任务：用户订阅（CronTrigger/DateTrigger，`max_instances=1`、`coalesce`）与后台采集（见 4.5）。订阅触发 `run_once(incremental=True)`：evidence 节点用 `sent_history` 按 `cluster_key` 过滤已推送簇，report 节点推送后回写账本，保证同一项目只推一次。

CLI `demo-incremental` 会创建一个带频率的订阅并连续触发两次：第一次生成新增 Word，第二次通过 `sent_history` 跳过已推送簇，用于录屏或验收时快速证明“定时增量不是一次性查询”。

P26 后订阅列表 API 会合并最近一次运行摘要：`last_new_count`、`last_skipped_sent`、最近 Word 下载地址、最近邮件状态和 `next_run_at`。Web 订阅页直接展示“新增/跳过历史/下次运行/最近 Word”，便于评审验证持续订阅是否真的做了增量过滤。

### 4.13 Word 报告与交付

文件：`tendertrace/report/{docx_writer,naming}.py`、`tendertrace/delivery/emailer.py`

按命名规范生成报告写入 `outputs/`，复制至 `outbox/` 并登记 `outbox_messages`；Web 端提供列表、下载与删除。P25 后报告新增运行漏斗、多源覆盖摘要和来源抓取健康表，使评审可以在 Word 中直接看到候选数、本地复用、外部来源新增、清洗去重、各来源命中、请求、成功、阻断与重试。

P26 增加可选 SMTP 邮件通道：当 `TENDERTRACE_DELIVERY_CHANNELS` 包含 `email` 且 SMTP 配置完整时，report 节点会将生成的 Word 作为附件发送，并把 `email_delivery` 写入运行统计。配置不完整时只记录 `skipped`，不影响 Web/outbox 交付；发送异常记录 `failed`，不回滚已生成报告。

P27 增加飞书多维表格台账通道：当 `TENDERTRACE_DELIVERY_CHANNELS` 包含 `feishu_bitable` 时，report 节点会把本次新增公告同步到飞书“招标机会”表，并把 `feishu_bitable_delivery` 写入运行统计。同步以 `项目指纹`（cluster_key）为去重键：不存在则新增为 `状态=新增`；已存在则只更新 `Word 报告`、`运行ID` 和 `最近同步时间`，避免覆盖业务人员在飞书里维护的 `已读/跟进中/忽略` 状态。也就是说，飞书里人工改为“跟进中”的机会不会被 TT 下次同步改回“新增”。CLI `feishu-bitable-check` 用于检查 token、Base、table_id 和字段完整性，`--ensure-fields` 会显式尝试补齐缺失字段。

### 4.14 评估体系（P23 升级）

文件：`tendertrace/evaluation.py`、`tendertrace/gold.py`

四维评测面板（`/api/evaluations/agent` 与 Web 仪表盘），总分四维等权（>=0.75 判 pass）：

- Harness：固定自然语言用例编译 BidQL 后逐槽位断言（字段准确率、用例通过率）；
- RAG：证据通过率、附件抽取率、报告产出率（来自近 200 次真实运行）；
- Agent：检查点完成率、失败率、平均事件数、模型审计数；
- Recall：金标集有标注时使用严格 Recall@10，否则使用代理分（0.45x源覆盖 + 0.35x去重保留 + 0.20x多源率），并明确标注 `strict_recall_available`。

金标框架：`docs/evaluation/gold_benchmark.json` 保存标注用例（查询 + 应召回公告全集）；`evaluate-gold` 计算 Recall@5/10、Precision@5/10 与漏召清单；`gold-candidates` 生成人工标注候选包。当前状态：10 个用例已建立，expected 标注待完成，完成后面板自动切换严格召回。

### 4.15 安全提交包

文件：`tendertrace/submission.py`

`package-submission` 生成脱敏提交包与 manifest：强制排除 `secrets/`、`.env.local` 等禁包条目，`acceptance-check` 校验禁包名单与交付完整性。

### 4.16 Web 工作台

目录：`web/dist`（原生 JS 静态页，FastAPI 托管）

能力：对话式查询输入、模型/检索/订阅控制、真实检查点进度（异步 `POST /api/runs/start`）、事件时间线、订阅与采集订阅管理、订阅增量摘要、最近 Word 直达下载、outbox 报告管理（含删除）、Agent 评测仪表盘、来源状态与模型自检、地域降级显式披露。

## 5. 数据库设计

SQLite 单文件（WAL），15 张表 + 1 张 FTS5 虚表：

| 表 | 职责 |
| --- | --- |
| notices | 公告主表（检索语料），含 canonical_url、snapshot_sha256、simhash64 |
| notices_fts | FTS5 全文索引虚表（jieba 分词；与主表行数对账触发重建） |
| notice_embeddings | 可选向量索引（model、dim、text_sha256、vector_json） |
| clusters | 项目簇（cluster_key、project_no、title_norm、related_sources_json） |
| evidence_items | 证据项（snapshot_sha256、excerpt、fact_checks_json、quality_score） |
| attachment_snapshots | 附件快照（sha256、bytes、text_excerpt、error） |
| runs / run_checkpoints / trace_events | 运行、检查点、事件流 |
| subscriptions / ingest_subscriptions | 用户订阅 / 采集订阅 |
| sent_history | 增量推送账本（subscription_id + cluster_key 唯一） |
| outbox_messages / model_audits / adapter_registry / schema_migrations | 投递、审计、注册、迁移 |

写路径以 INSERT OR REPLACE / UPSERT 保证幂等；JSON 弹性字段承载扩展结构，规避频繁 DDL 迁移。

## 6. 创新点

### 6.1 规则主导、模型增强

主链路确定性，LLM 仅在查询侧追加词条且受白名单约束，失败自动降级，保证可复现与故障隔离。

### 6.2 两级检索架构

后台采集入库 + FTS5/向量本地检索优先 + 现场补采兜底：拆除“单次抓取页数 = 召回上限”的天花板，高频查询秒级返回，补采结果回流使语料自增长。

### 6.3 证据优先报告

任何进入报告的内容必须可回指原文：快照哈希 + 逐字段事实校验 + 附件快照，生成端不使用 LLM，零幻觉。

### 6.4 登录态可复用但不保存密码

人工合规登录后仅保存浏览器 storage_state，会话可校验、可过期、可刷新，密码与验证码不进入系统。

### 6.5 增量推送以项目簇为主键

以 cluster_key（项目维度）而非单条公告做推送判重，跨站转载不会造成重复推送。

### 6.6 评估可信化

金标集严格 Recall@K 框架与代理指标并存且显式标注可用性，不虚报召回率；评测面板基于真实运行数据持续计算。

## 7. 安全与合规边界

- 不破解验证码、不绕过付费墙、不获取免费会员不可见内容。
- 密钥仅存 `.env.local`（gitignore），配置摘要只暴露“是否配置”。
- 模型错误信息脱敏，审计不落原文。
- `secrets/` 强制排除在提交包外，outbox 下载做文件名校验防路径穿越。
- 已知缺口：REST API 无认证鉴权，多用户或公网部署前必须补齐。

## 8. 可验证性

- 95 个单元测试（含 retrieval / ingest / gold / vector / ingest_subscriptions 新模块），关键外部依赖协议化注入，测试不出网。
- Ruff 静态检查通过。
- `acceptance-check` 交付审计、`demo-check` 录制预检、`package-submission` 禁包校验。
- trace_events + run_checkpoints 支持任意历史运行逐节点回放，自证无硬编码。
- `evaluate-gold` 输出可复现的召回评测快照（docs/evaluation/）。

## 9. 当前限制与后续方向

当前限制：

- 金标集 10 个用例尚未完成人工标注，严格 Recall@K 未激活，面板召回项仍为代理分。
- 向量检索默认关闭，语义召回增益未验证。
- 本地库覆盖度受 ingest 主题池 x 地区池配置限制，池外查询退化为现场补采。
- 负向词过滤在 SQL 中使用 LIKE 全文扫描，库增大后有性能压力。
- 多源补采串行执行；SQLite 存在写并发与体量上限。

后续方向：

- 完成金标标注激活严格召回基线；启用向量通道并 A/B 验证增益。
- 公告类型离线分类打标替代负向词 LIKE；采集并行化；API 鉴权。
- 条件路由反思循环（质量不达标回炉补采）；LLM 摘要 + 事实回查闭环。
- 飞书集成（群推送 / 云文档 / 多维表格）；数据源声明式插件化。
- 规模化演进：PostgreSQL + 任务队列 + 对象存储。
